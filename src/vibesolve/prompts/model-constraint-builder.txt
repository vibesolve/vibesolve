Core concepts (quick reference) - key annotations
- @PlanningSolution - Solution class, Wraps the entire problem + solution
- @PlanningEntity - Entity class (Shift), Class the solver modifies
- @PlanningVariable - Field on entity, The field the solver changes
- @PlanningListVariable - List field on entity, The field the solver changes
- @PlanningScore - Score field on solution, Where solver writes the score
- @PlanningId - ID field on entities & facts, Required for testing & ProblemChange
- @ProblemFactCollectionProperty - List fields on solution, Collections of fixed facts
- @PlanningEntityCollectionProperty - List field on solution, Collection of planning entities
- @ValueRangeProvider - List field on solution, Possible values for a planning variable
- @PlanningPin - Boolean field on entity, If true, solver won't change this entity

---

Here is a more detailed description of available annotations:

## Decision: Problem Fact vs Planning Entity

Every domain class falls into one of three categories:

1. **Unrelated** — not referenced by any constraint. Ignore it.
2. **Problem fact** — used by constraints but does NOT change during solving. No Timefold annotations needed. Examples: `Employee`, `Availability`, `Timeslot`, `Room`.
3. **Planning entity** — used by constraints AND changes during solving. Annotated with `@PlanningEntity`. The fields that the solver changes are **planning variables**.

**The key question: "What class has a field I want the solver to fill in for me?"** That class is the planning entity. In employee scheduling, a `Shift` has an `employee` field that starts as `null` and gets assigned by the solver — so `Shift` is the planning entity.

> **Important:** Choose the model where the number of planning entities is fixed. In employee scheduling, the number of shifts is known in advance (fixed), but the number of shifts per employee is not. Therefore `Shift` is the entity and `Employee` is the value — not the other way around.

## @PlanningId

```java
import ai.timefold.solver.core.api.domain.lookup.PlanningId;
```

Marks the unique identifier field on both problem facts and planning entities. Required for multi-threaded solving, real-time planning, and `SolutionManager.analyze()`.

```java
@PlanningId
private String id;
```

Requirements:
- Must be unique within that class (different classes can share the same ID value)
- Must never be `null` when `Solver.solve()` is called

---

## @PlanningEntity

```java
import ai.timefold.solver.core.api.domain.entity.PlanningEntity;
```

Marks a class whose instances change during solving. Must have at least one `@PlanningVariable` or `@PlanningListVariable` field and a **public no-arg constructor**.

```java
@PlanningEntity
public class Shift {

    @PlanningId
    private String id;

    // Problem properties — do NOT change during solving
    private LocalDateTime start;
    private LocalDateTime end;
    private String location;
    private String requiredSkill;

    // Planning variable — the solver assigns this
    @PlanningVariable(valueRangeProviderRefs = "employeeRange")
    private Employee employee;

    // REQUIRED: no-arg constructor
    public Shift() {
    }

    public Shift(String id, LocalDateTime start, LocalDateTime end,
                 String location, String requiredSkill) {
        this.id = id;
        this.start = start;
        this.end = end;
        this.location = location;
        this.requiredSkill = requiredSkill;
    }

    // Getters and setters for ALL fields (required by Timefold)
    // ...
}
```

### Optional: Pinning filter

To prevent the solver from changing certain entities (e.g., already-published shifts), use a pinning filter:

```java
@PlanningEntity(pinningFilter = ShiftPinningFilter.class)
public class Shift { ... }
```

See [@PlanningPin](#planningpin) for the modern boolean-field alternative.

### Optional: Difficulty comparator

Helps Construction Heuristics assign harder entities first:

```java
@PlanningEntity(difficultyComparatorClass = ShiftDifficultyComparator.class)
public class Shift { ... }
```

The comparator should order entities ascending (easy → hard). Do not reference planning variable values in the comparator.

## @PlanningVariable

```java
import ai.timefold.solver.core.api.domain.variable.PlanningVariable;
```

Marks a field on a `@PlanningEntity` whose value the solver assigns. The solver picks values from a `@ValueRangeProvider` that returns the same type and has the same id.

```java
@PlanningVariable(valueRangeProviderRefs = "employeeRange")
private Employee employee;
```

The field must have both a getter and setter. It starts as `null` (unassigned) and the solver fills it in.

### Type matching

**ALWAYS include `valueRangeProviderRefs` in every `@PlanningVariable()` annotation. It MUST point to the exact string `id` declared on the matching `@ValueRangeProvider`. ALWAYS declare `@ValueRangeProvider(id = "...")` on the solution class. Never rely on Timefold auto-connecting by type — always wire them explicitly.**

Please never write comments inside annotations like this: @PlanningVariable(valueRangeProviderRefs = {"teacherRange"}, /*allowsUnassigned*/)

// In Entity class:
@PlanningVariable(valueRangeProviderRefs = "timeSlotRange")  // <-- Must match
private TimeSlot timeSlot;

@ValueRangeProvider(id = "timeSlotRange")  // <-- ID here — ALWAYS declare the id
public List<TimeSlot> getTimeSlots() { ... }

### Allowing unassigned values (overconstrained planning)

By default, every planning variable must be assigned after solving. For overconstrained problems (more shifts than employees can fill), allow `null`:

```java
@PlanningVariable(valueRangeProviderRefs = "employeeRange", allowsUnassigned = true)
private Employee employee;
```

**Two obligations come with this flag — both are mandatory:**

1. Every constraint rooted in this entity must use `forEachIncludingUnassigned(...)`, not `forEach(...)`, with null guards in the filters. `forEach()` drops entities that have an unassigned variable, so leaving it in place makes every constraint on this entity match nothing. See "CRITICAL RULE: forEach() silently skips entities with unassigned variables" in PART B.
2. There must be a scoring constraint that makes assignment worth something — typically a medium-level reward for each assigned entity, or a medium-level penalty for each one left null. Without it the solver has no reason to ever assign the variable, and obligation 1 becomes the difference between a working solver and one that scores `0hard/0soft` on everything.

Only use `allowsUnassigned = true` when the ProblemSpec actually permits the thing to be left unassigned. It is not a safety net.

### Multiple @PlanningVariable fields on one entity

A single `@PlanningEntity` can have **multiple independent** `@PlanningVariable` fields. Timefold assigns each independently. This is common when an entity needs both a time slot and a room, or both a crew and a start date:

```java
@PlanningEntity
public class MeetingAssignment {

    @PlanningVariable(valueRangeProviderRefs = "timeGrainRange")
    private TimeGrain startingTimeGrain;

    @PlanningVariable(valueRangeProviderRefs = "roomRange")
    private Room room;
}
```

**Warning — this is where `forEach()` bites hardest.** `forEach(MeetingAssignment.class)` emits an entity only when *all* of its planning variables are assigned. If one of several variables is marked `allowsUnassigned = true` and nothing in the score rewards assigning it, the solver leaves it null on every entity, and every constraint rooted in that entity — not just the ones about that variable — matches nothing. Give every variable on a multi-variable entity a reason to be assigned, and read "CRITICAL RULE: forEach() silently skips entities with unassigned variables" in PART B before writing the provider.

**Each variable needs its own `@ValueRangeProvider(id = "...")` on the solution class with an id that exactly matches the `valueRangeProviderRefs` on the entity.** Both are assigned independently by the solver. The solution class must look like this:

```java
@PlanningSolution
public class MeetingSchedule {

    @ValueRangeProvider(id = "timeGrainRange")
    @ProblemFactCollectionProperty
    private List<TimeGrain> timeGrains;

    @ValueRangeProvider(id = "roomRange")
    @ProblemFactCollectionProperty
    private List<Room> rooms;

    @PlanningEntityCollectionProperty
    private List<MeetingAssignment> meetings;

    @PlanningScore
    private HardSoftScore score;
}
```

## @PlanningListVariable

```java
import ai.timefold.solver.core.api.domain.variable.PlanningListVariable;
```

For problems where an entity contains an **ordered list** of values (e.g., vehicle routing: a Vehicle has an ordered list of Visits). The solver decides both the assignment and the ordering.

```java
@PlanningEntity
public class Vehicle {
    @PlanningListVariable(valueRangeProviderRefs = "visitRange")
    private List<Visit> visits = new ArrayList<>();
}
```

> **For employee scheduling, use `@PlanningVariable`, NOT `@PlanningListVariable`.** List variables are for routing-style problems where a single entity "owns" an ordered sequence. In employee scheduling, you assign one employee per shift — that's a basic `@PlanningVariable`.

### @PlanningListVariable — valueRangeProviderRefs

**`@PlanningListVariable` takes `valueRangeProviderRefs` exactly like `@PlanningVariable`. ALWAYS declare it, and ALWAYS declare the matching `@ValueRangeProvider(id = "...")` on the solution class.**

```java
// CORRECT — always declare valueRangeProviderRefs
@PlanningListVariable(valueRangeProviderRefs = "visitRange")
private List<Visit> visits = new ArrayList<>();
```

The solution class MUST have a matching `@ValueRangeProvider(id = "visitRange")` on the element collection — see the VehicleRoutePlan example below.

### @PlanningListVariable — allowsUnassignedValues

`allowsUnassignedValues` defaults to `false`, which means Timefold requires **every** value in the range to appear in exactly one list. The solver cannot leave anything out, no matter how badly it fits.

If the ProblemSpec says some values may or should be left out — "not everything can be scheduled", "select a subset", "unassigned entries are allowed and expected", demand exceeding capacity — you MUST set the flag, otherwise the requirement is not merely unimplemented, it is unrepresentable:

```java
@PlanningListVariable(valueRangeProviderRefs = "visitRange", allowsUnassignedValues = true)
private List<Visit> visits = new ArrayList<>();
```

Then add the scoring constraint that makes selection meaningful — a medium-level reward per value that does get placed, weighted by its importance. Without that reward the solver has no reason to place anything at all. With the flag left at `false` and no reward, the solver's only way to handle a value it cannot fit is to jam it in anyway, past the end of every capacity window.

When to use which:

| Pattern | Annotation | Example |
|---------|-----------|---------|
| Assign one value to each entity | `@PlanningVariable` | Shift → Employee |
| Assign an ordered list of values to each entity | `@PlanningListVariable` | Vehicle → List\<Visit\> |

## @PlanningSolution

```java
import ai.timefold.solver.core.api.domain.solution.PlanningSolution;
```

Marks the container class that holds the entire problem and its solution. It has four required component types:

1. `@PlanningEntityCollectionProperty` — all entity instances
2. `@ProblemFactCollectionProperty` — all problem fact instances
3. `@ValueRangeProvider` — possible values for planning variables
4. `@PlanningScore` — the score field

```java
@PlanningSolution
public class EmployeeSchedule {

    @ValueRangeProvider(id = "employeeRange")
    @ProblemFactCollectionProperty
    private List<Employee> employees;

    @ProblemFactCollectionProperty
    private List<Availability> availabilities;

    @PlanningEntityCollectionProperty
    private List<Shift> shifts;

    @PlanningScore
    private HardSoftScore score;

    // REQUIRED: no-arg constructor
    public EmployeeSchedule() {
    }

    public EmployeeSchedule(List<Employee> employees,
                            List<Availability> availabilities,
                            List<Shift> shifts) {
        this.employees = employees;
        this.availabilities = availabilities;
        this.shifts = shifts;
    }

    // Getters and setters for ALL fields
    // ...
}
```

> **Note:** `@ValueRangeProvider` and `@ProblemFactCollectionProperty` can be on the same field. The `employees` field above serves double duty: it provides the value range for `Shift.employee` (matched by the explicit `id = "employeeRange"` in `@ValueRangeProvider` and `valueRangeProviderRefs = "employeeRange"` in `@PlanningVariable`) AND registers employees as problem facts accessible in constraints.

## @ValueRangeProvider

```java
import ai.timefold.solver.core.api.domain.valuerange.ValueRangeProvider;
```

Declares a collection of possible values for a `@PlanningVariable`. Placed on a field or getter in the `@PlanningSolution` class.

```java
@ValueRangeProvider(id = "employeeRange")
private List<Employee> employees;
```

### Entity-local @ValueRangeProvider

`@ValueRangeProvider` can also be placed on an **instance method of the `@PlanningEntity`** itself. This restricts each entity to its own valid subset of values rather than the global list. **Always declare an explicit `id` on `@ValueRangeProvider` and always reference it via `valueRangeProviderRefs` on `@PlanningVariable`.**

```java
@PlanningEntity
public class Talk {

    private List<Timeslot> compatibleTimeslots;  // populated from input data
    private List<Room> compatibleRooms;

    // Entity-local range: only timeslots compatible with THIS talk
    @ValueRangeProvider(id = "timeslotRange")
    public List<Timeslot> getCompatibleTimeslots() {
        return compatibleTimeslots;
    }

    @ValueRangeProvider(id = "roomRange")
    public List<Room> getCompatibleRooms() {
        return compatibleRooms;
    }

    @PlanningVariable(valueRangeProviderRefs = "timeslotRange")
    private Timeslot timeslot;

    @PlanningVariable(valueRangeProviderRefs = "roomRange")
    private Room room;
}
```

Use entity-local ranges when different entity instances have **different valid value sets**. Use solution-level ranges when all entities draw from the same global pool.

### @PlanningEntity as @ValueRangeProvider source

A `@PlanningEntityCollectionProperty` list can also be annotated with `@ValueRangeProvider` when other entities need to pick from it. Both annotations on the same field are valid:

```java
@PlanningSolution
public class VehicleRoutePlan {

    @PlanningEntityCollectionProperty      // Visit is an entity (has shadow variables)
    @ValueRangeProvider(id = "visitRange") // AND the value range for Vehicle.visits — ALWAYS declare the id
    private List<Visit> visits;
}
```

## @ProblemFactProperty

```java
import ai.timefold.solver.core.api.domain.solution.ProblemFactProperty;
```

For a **single** (non-collection) problem fact — a singleton config or parameter object that constraints need to reference. Use `@ProblemFactCollectionProperty` for lists; use `@ProblemFactProperty` for a single instance.

```java
@ProblemFactProperty
private WorkCalendar workCalendar;
```

If this field is null at solve time, any constraint that calls `forEach(WorkCalendar.class)` will simply see an empty stream (not a crash). However, shadow variable suppliers that access it via a field reference WILL throw NPE if it is null — always initialize it in the DataGenerator.

## @ProblemFactCollectionProperty

```java
import ai.timefold.solver.core.api.domain.solution.ProblemFactCollectionProperty;
```

Registers a collection of problem facts so they can be queried in constraint streams via `forEach()` and `join()`.

```java
@ProblemFactCollectionProperty
private List<Availability> availabilities;
```

Every class you reference in a constraint (`forEach`, `join`, `ifExists`) must be registered either as a `@ProblemFactCollectionProperty` or as a `@PlanningEntityCollectionProperty`.

For a singleton problem fact (not a collection), use `@ProblemFactProperty` instead.

Do not mix up @ProblemFactCollectionProperty (or @ProblemFactProperty) with @PlanningEntityCollectionProperty. If the class is annotated with @PlanningEntity then the list must be annotated with @PlanningEntityCollectionProperty. This is important.

## @PlanningEntityCollectionProperty

```java
import ai.timefold.solver.core.api.domain.solution.PlanningEntityCollectionProperty;
```

Registers the collection of planning entities. The solver iterates over these to assign planning variables.

```java
@PlanningEntityCollectionProperty
private List<Shift> shifts;
```

This list must contain ALL entity instances. Do not filter it.

---

## CRITICAL: Choosing @PlanningEntityCollectionProperty vs @ProblemFactCollectionProperty

**Rule:** Use `@PlanningEntityCollectionProperty` for EVERY class annotated with `@PlanningEntity`. Use `@ProblemFactCollectionProperty` for every OTHER class that constraints need to reference (Availability, Room, Timeslot, Employee, etc.).

**The mistake to avoid:** If a class is annotated with `@PlanningEntity`, you MUST use `@PlanningEntityCollectionProperty` on the solution field that holds instances of it — even if the class sounds like a data class (e.g., "Task", "Job", "Operation"). Using `@ProblemFactCollectionProperty` on a `@PlanningEntity` list causes a runtime error:

```
"factCollectionProperty (taskList) returns a collection with an element that is a planning entity."
```

**Checklist before writing the solution class:**
1. List all your `@PlanningEntity` classes.
2. For each: add a `List<X>` field in `@PlanningSolution` with `@PlanningEntityCollectionProperty`.
3. For each class referenced in constraints that is NOT a `@PlanningEntity`: add a `List<X>` field with `@ProblemFactCollectionProperty`.
4. Ensure EVERY `@ProblemFactCollectionProperty` field is initialized (never null — use `new ArrayList<>()` if empty).
5. Add a `SolverStatus solverStatus` field for REST-based projects so the REST resource can report solver progress. This is NOT a Timefold solver field — it is a plain field managed by the REST layer:
```java
import ai.timefold.solver.core.api.solver.SolverStatus;

@PlanningSolution
public class MySchedule {
    // ... Timefold fields ...

    private SolverStatus solverStatus;

    public SolverStatus getSolverStatus() { return solverStatus; }
    public void setSolverStatus(SolverStatus solverStatus) { this.solverStatus = solverStatus; }
}
```

## @PlanningScore

```java
import ai.timefold.solver.core.api.domain.solution.PlanningScore;
import ai.timefold.solver.core.api.score.buildin.hardsoft.HardSoftScore;
```

The score field where Timefold stores the quality of the current solution. Starts as `null`; Timefold fills it in.

```java
@PlanningScore
private HardSoftScore score;
```

Score types (most common first):

| Type | Levels | Use when |
|------|--------|----------|
| `HardSoftScore` | 2 (hard, soft) | The default. Hard = must not break. Soft = prefer not to break. |
| `HardMediumSoftScore` | 3 (hard, medium, soft) | The ProblemSpec ranks its objectives into two tiers above the tie-breakers — "primary/secondary", "more important than", explicit priority groups. Medium = the primary goal (coverage, selection, meeting targets). Soft = tie-breakers (fairness, balance, utilization). |

**Default to `HardSoftScore`; use `HardMediumSoftScore` when the spec ranks its objectives** — see "Score Level Strategy" in PART B. Whichever you pick, use it consistently across the `@PlanningScore` field, every `.penalize`/`.reward` call and the `SolutionManager` generic parameter. If a weigher returns a `long`, cast it to `int` (e.g., scale down or cast explicitly).

## @PlanningPin

```java
import ai.timefold.solver.core.api.domain.entity.PlanningPin;
```

A boolean field on a `@PlanningEntity`. When `true`, the solver will not change this entity's planning variables. Used for continuous planning (locking already-published assignments).

```java
@PlanningEntity
public class Shift {

    @PlanningPin
    private boolean pinned;

    @PlanningVariable
    private Employee employee;
}
```

When `pinned == true`, the solver treats this Shift as immutable. The employee assignment stays as-is.

For most generated projects, do NOT implement pinning unless the problem spec explicitly requires it.

## Shadow Variables

A shadow variable is derived from genuine planning variables. It's automatically updated when genuine variables change. Employee scheduling typically does NOT need shadow variables — they're mainly used in routing problems.

### CRITICAL: @JsonIgnore on entity-reference shadow variables (prevents circular reference crash)

Always add `@JsonIgnore` to every shadow variable field.** Shadow variables are computed by Timefold at runtime. They are NOT needed as input, and they always create circular references that cause Jackson to throw `JsonMappingException: Document nesting depth exceeds maximum` at the first REST call. Every field annotated with `@InverseRelationShadowVariable`, `@AnchorShadowVariable`, `@PreviousElementShadowVariable`, `@NextElementShadowVariable`, or any other shadow variable annotation MUST also have `@JsonIgnore`. No exceptions.
Shadow variables that reference another entity create a bidirectional cycle: `Vehicle → visits → Visit → vehicle → Vehicle → ...`. Jackson will follow this cycle until it hits the nesting limit and throws a `JsonMappingException`. Shadow variables are computed by Timefold and do NOT need to be serialized — they are recomputed from scratch each time a problem is loaded.

**Rule:** Every shadow variable field whose type is an entity or another planning element MUST be annotated with `@JsonIgnore`. This applies to:
- `@InverseRelationShadowVariable` — always references the owner entity back → always `@JsonIgnore`
- `@PreviousElementShadowVariable` — references the previous element (same type) → always `@JsonIgnore`
- `@NextElementShadowVariable` — references the next element (same type) → always `@JsonIgnore`
- `@ShadowVariable` whose return type is an entity class → `@JsonIgnore`

`@ShadowVariable` fields whose return type is a plain value (`LocalDateTime`, `int`, `String`, etc.) do NOT cause circular references and do NOT need `@JsonIgnore`.

```java
// Correct — @JsonIgnore on every entity-reference shadow variable
import com.fasterxml.jackson.annotation.JsonIgnore;

@PlanningEntity
public class Visit {
    @InverseRelationShadowVariable(sourceVariableName = "visits")
    @JsonIgnore   // ← prevents Vehicle→Visit→Vehicle cycle
    private Vehicle vehicle;

    @PreviousElementShadowVariable(sourceVariableName = "visits")
    @JsonIgnore   // ← prevents Visit→Visit→Visit cycle
    private Visit previousVisit;

    @ShadowVariable(supplierName = "arrivalTimeSupplier")
    private LocalDateTime arrivalTime;  // value type — no @JsonIgnore needed
}
```

Add `import com.fasterxml.jackson.annotation.JsonIgnore;` to every domain class that uses this annotation.

### @InverseRelationShadowVariable

Creates a bi-directional relationship. If `Shift.employee` is a `@PlanningVariable`, you can add an inverse collection on `Employee`:

```java
import ai.timefold.solver.core.api.domain.variable.InverseRelationShadowVariable;
import com.fasterxml.jackson.annotation.JsonIgnore;

@PlanningEntity  // Must be annotated even though it's a "shadow" entity
public class Employee {

    @InverseRelationShadowVariable(sourceVariableName = "employee")
    @JsonIgnore
    private List<Shift> shifts = new ArrayList<>();
}
```

The `shifts` list is auto-maintained by Timefold. The `sourceVariableName` must match the field name on the entity that references this class.

> **Important:** The shadow collection must be initialized (not null) and mutable.

### Other shadow variable types (routing-focused)

These are mainly used with `@PlanningListVariable` for routing problems:

- `@PreviousElementShadowVariable` — the previous element in a list variable
- `@NextElementShadowVariable` — the next element in a list variable (see example below)
- `@AnchorShadowVariable` — the anchor (e.g., vehicle/depot) of a chain
- `@ShadowVariable(supplierClass = ...)` — custom shadow via a `VariableListener`

**`@NextElementShadowVariable` example** (order-picking pattern):
```java
import ai.timefold.solver.core.api.domain.variable.NextElementShadowVariable;
import com.fasterxml.jackson.annotation.JsonIgnore;

@PlanningEntity
public class PickTask {

    // The @PlanningListVariable is on Trolley.pickTasks
    @InverseRelationShadowVariable(sourceVariableName = "pickTasks")
    @JsonIgnore
    private Trolley trolley;

    @PreviousElementShadowVariable(sourceVariableName = "pickTasks")
    @JsonIgnore
    private PickTask previousPickTask;

    // Gives each task a reference to the one AFTER it in the route.
    // null means this is the last task assigned to the trolley.
    @NextElementShadowVariable(sourceVariableName = "pickTasks")
    @JsonIgnore
    private PickTask nextPickTask;
}
```

Use `@NextElementShadowVariable` when a task needs to know what comes after it — for example, to check if it is the last stop, or to compute downstream travel cost. The `sourceVariableName` must match the `@PlanningListVariable` field name on the owner entity.

## No-Arg Constructor Requirement

Every class annotated with `@PlanningEntity` or `@PlanningSolution` **MUST** have a public no-arg constructor. Timefold uses it internally for cloning solutions during solving.

```java
// Correct
@PlanningEntity
public class Shift {
    public Shift() {}                      // no-arg constructor
    public Shift(String id, ...) { ... }   // convenience constructor
}

// WRONG — will throw exception at startup
@PlanningEntity
public class Shift {
    public Shift(String id, ...) { ... }   // no no-arg constructor!
}
```

Problem fact classes (without `@PlanningEntity`) do NOT need a no-arg constructor.

### Visit.java — Planning Entity

```java
package org.acme.vehiclerouting.domain;

import ai.timefold.solver.core.api.domain.entity.PlanningEntity;
import ai.timefold.solver.core.api.domain.lookup.PlanningId;
import ai.timefold.solver.core.api.domain.variable.InverseRelationShadowVariable;
import ai.timefold.solver.core.api.domain.variable.PreviousElementShadowVariable;
import ai.timefold.solver.core.api.domain.variable.ShadowSources;
import ai.timefold.solver.core.api.domain.variable.ShadowVariable;
import lombok.*;

import java.time.Duration;
import java.time.LocalDateTime;
import java.time.temporal.ChronoUnit;

@NoArgsConstructor
@Getter @Setter
@PlanningEntity
public class Visit {

    @PlanningId
    private long id;
    private Location location;
    private int demand;
    private LocalDateTime minStartTime;
    private LocalDateTime maxEndTime;
    private Duration serviceDuration;

    @InverseRelationShadowVariable(sourceVariableName = "visits")
    @JsonIgnore  // REQUIRED: prevents circular reference Vehicle→visits→Visit→vehicle→...
    private Vehicle vehicle;

    @PreviousElementShadowVariable(sourceVariableName = "visits")
    @JsonIgnore  // REQUIRED: prevents circular reference Visit→previousVisit→previousVisit→...
    private Visit previousVisit;

    // Shadow variable: arrival time computed by a supplier method.
    // BOTH @ShadowVariable(supplierName = "arrivalTimeSupplier") on the field AND
    // @ShadowSources on the method are required — omitting either causes a startup error.
    @ShadowVariable(supplierName = "arrivalTimeSupplier")
    private LocalDateTime arrivalTime;  // value type — no circular reference risk, no @JsonIgnore needed

    public Visit(long id, Location location, int demand,
                 LocalDateTime minStartTime, LocalDateTime maxEndTime, Duration serviceDuration) {
        this.id = id;
        this.location = location;
        this.demand = demand;
        this.minStartTime = minStartTime;
        this.maxEndTime = maxEndTime;
        this.serviceDuration = serviceDuration;
    }

    // Called automatically by Timefold when vehicle or previousVisit.arrivalTime changes.
    @ShadowSources({"vehicle", "previousVisit.arrivalTime"})
    public LocalDateTime arrivalTimeSupplier() {
        if (previousVisit == null && vehicle == null) return null;
        LocalDateTime departure = previousVisit == null
                ? vehicle.getDepartureTime()
                : previousVisit.getDepartureTime();
        return departure != null
                ? departure.plusSeconds(getDrivingTimeSecondsFromPreviousStandstill())
                : null;
    }

    public LocalDateTime getDepartureTime() {
        if (arrivalTime == null) return null;
        LocalDateTime startService = arrivalTime.isBefore(minStartTime) ? minStartTime : arrivalTime;
        return startService.plus(serviceDuration);
    }

    public long getDrivingTimeSecondsFromPreviousStandstill() {
        if (vehicle == null) throw new IllegalStateException("Shadow variables not initialized yet.");
        if (previousVisit == null) return vehicle.getHomeLocation().getDistance(location);
        return previousVisit.getLocation().getDistance(location);
    }
}
```

### Vehicle.java — Planning Entity

```java
package org.acme.vehiclerouting.domain;

import ai.timefold.solver.core.api.domain.entity.PlanningEntity;
import ai.timefold.solver.core.api.domain.lookup.PlanningId;
import ai.timefold.solver.core.api.domain.variable.PlanningListVariable;
import lombok.*;

import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

@PlanningEntity
@NoArgsConstructor @AllArgsConstructor
@Getter @Setter
public class Vehicle {

    @PlanningId
    private long id;

    private Location homeLocation;
    private int capacity;
    private LocalDateTime departureTime;

    @PlanningListVariable
    private List<Visit> visits;

    public Vehicle(long id, Location homeLocation, int capacity, LocalDateTime departureTime) {
        this.id = id;
        this.homeLocation = homeLocation;
        this.capacity = capacity;
        this.departureTime = departureTime;
        this.visits = new ArrayList<>();
    }

    public int getTotalDemand() {
        int totalDemand = 0;
        for (Visit visit : visits) {
            totalDemand += visit.getDemand();
        }
        return totalDemand;
    }

    public int getTotalDistanceTravelled() {
        if (visits.isEmpty()) {
            return 0;
        }

        int totalDrivingDistance = 0;
        Location previousLocation = homeLocation;

        for (Visit visit : visits) {
            totalDrivingDistance += previousLocation.getDistance(visit.getLocation());
            previousLocation = visit.getLocation();
        }
        totalDrivingDistance += previousLocation.getDistance(homeLocation);

        return totalDrivingDistance;
    }
}
```

**Key rules for routing models:**
- `Visit` must be `@PlanningEntity` (not just a problem fact) because it holds shadow variables. Without `@PlanningEntity` on `Visit`, the shadow variable annotations are ignored.
- `@InverseRelationShadowVariable(sourceVariableName = "visits")` on `Visit.vehicle` — the `sourceVariableName` must exactly match the field name of the `@PlanningListVariable` on `Vehicle`.
- `@PreviousElementShadowVariable(sourceVariableName = "visits")` on `Visit.previousVisit` — gives each visit a reference to the one before it in the route; `null` means it is the first visit.
- `@ShadowVariable(supplierName = "arrivalTimeSupplier")` — the `supplierName` must match the method name on the same class annotated with `@ShadowSources`. BOTH annotations are required: the field gets `@ShadowVariable(supplierName = "methodName")` AND the method gets `@ShadowSources(...)`. Omitting `@ShadowSources` on the method causes: `Method "arrivalTimeSupplier" referenced from @ShadowVariable is not annotated with @ShadowSources`.
- `@ShadowSources({"vehicle", "previousVisit.arrivalTime"})` declares which planning/shadow variables trigger recomputation. The method itself computes and returns the new value. For collection fields, use bracket notation to watch a field on every element: `@ShadowSources("predecessorAllocations[].endDate")` — this re-triggers when any element's `endDate` changes.

VehicleRoutePlan (@PlanningSolution)
├── vehicles: List<Vehicle>          ← @PlanningEntityCollectionProperty

Additional DataGenerator instructions:
- Before calling any getter method on a domain class, verify the getter exists in the ProjectManifest domain class. Never invent getter names. If the domain class has a field `startTime`, the getter is `getStartTime()` — do not assume alternative names like `getEarliestStartMinute()` or `getBeginTime()` unless they are explicitly present in the manifest.
- Initialize ALL `@ProblemFactCollectionProperty`-backed list fields in the `@PlanningSolution` constructor or builder to an empty list or a generated list — never leave them null. A null collection causes "factCollectionProperty should never return null" at runtime.
- Initialize ALL `@PlanningListVariable` fields (e.g., `vehicle.visits`, `employee.tasks`) to `new ArrayList<>()` in the domain class constructor. If the field is null when the solver starts, it will throw a NullPointerException when trying to add elements.
- If the solution has a `@ProblemFactProperty` singleton field (a single config/calendar object, not a list), always create and set it in the DataGenerator. A null singleton will cause NPE in any constraint or shadow variable that references it.

DataGenerator related common errors:

ERROR: The supply for list variable (Van.visits) is corrupted, because the element (C1) at index (0) already exists.
NEVER pre-populate a @PlanningListVariable list in the DataGenerator. The solver manages all assignments internally. If the DataGenerator adds elements to the list (e.g., vehicle.getVisits().add(visit)), the solver's internal tracking becomes inconsistent and throws this corruption error. Always leave the list as new ArrayList<>() when handing the solution to the solver. Let the solver do all the assigning.

ERROR: java.lang.IllegalStateException: The fact (...) is already inserted.
This happens when the same object instance is added to BOTH the planning entity list AND a problem fact list. Each object must appear in exactly ONE of the two. For example, if Route objects are @PlanningEntity, they must ONLY be in the routeList (@PlanningEntityCollectionProperty), not in any other list annotated with @ProblemFactCollectionProperty.

ERROR: @PlanningId value (1) is already used by another planning entity.
Every @PlanningId value must be globally unique within its class. When generating entities in a loop, use a counter or UUID to ensure uniqueness:
  entity.setId(String.valueOf(idCounter++));
Do not reuse the same id across different instances.

ERROR: factCollectionProperty (availabilities) should never return null.
Every collection annotated with @ProblemFactCollectionProperty or @PlanningEntityCollectionProperty must be initialized to at least an empty list. Even if you generate 0 records, the field must be new ArrayList<>(), never null.

ERROR: java: local variables referenced from a lambda expression must be final or effectively final. On code:
for (int d = 0; d < days; d++) {
    List<TimeSlot> slots = timeSlotList.stream().filter(ts -> ts.getDayIndex() == d).collect(Collectors.toList());
}

Notice the d variable in the filter, that's the error.
A quick workaround is something like this:
for (int d = 0; d < days; d++) {
    int finalDay = d;
    List<TimeSlot> slots = timeSlotList.stream().filter(ts -> ts.getDayIndex() == finalDay).collect(Collectors.toList());
}

Important:
- **Prefer Lombok for getters and setters.** Use `@Getter` and `@Setter` at the class level (or field level) instead of writing explicit getter/setter methods, UNLESS the getter or setter contains custom logic (a null check, a computation, a derived value, etc.). A simple `return field;` or `this.field = value;` must always be replaced by Lombok. Always add the correct Lombok imports (`import lombok.Getter;`, `import lombok.Setter;`, `import lombok.NoArgsConstructor;`, `import lombok.AllArgsConstructor;`). If a class already uses Lombok annotations, do NOT also write out the getters/setters manually — pick one approach and stick to it.
  - Use class-level `@Getter @Setter` when ALL fields need simple accessors.
  - Use field-level `@Getter` / `@Setter` when only some fields need them (e.g., a `@JsonIgnore` field that only needs a getter).
  - Write explicit methods ONLY when there is logic beyond a simple return/assignment (e.g., `getDate()` derived as `start.toLocalDate()`, a setter that also updates a related field).
  - **NEVER use `@AllArgsConstructor` on `@PlanningEntity` classes that have shadow variables** (`@InverseRelationShadowVariable`, `@PreviousElementShadowVariable`, `@ShadowVariable`). `@AllArgsConstructor` generates a constructor that includes every field — including shadow variable fields that must always be `null` at construction time (they are managed by the solver). This causes an argument-count mismatch when the DataGenerator calls the constructor with only the problem-fact fields. Instead: annotate the class with `@NoArgsConstructor @Getter @Setter` and write an explicit partial constructor that takes only the non-shadow-variable fields, leaving shadow variables to default to `null`. `@AllArgsConstructor` is safe for **problem fact classes** (no shadow variables).
- Ensure every planning entity has at least one problem property (a field that is NOT a planning variable). A planning entity cannot consist solely of planning variables + ID.
- Minimize planning variables. Every additional planning variable exponentially increases the search space. If one variable can be derived from another, make it a shadow variable.
- The class that changes during planning is the planning entity. The field that the solver fills in is the planning variable.

## CRITICAL RULE: forEach() silently skips entities with unassigned variables

`factory.forEach(MyEntity.class)` only emits entities whose genuine planning
variables are ALL assigned. An entity with a variable left `null` is invisible
to that stream — no error, no warning, no match. `forEachUniquePair(...)` and
`forEachIncludingNullVars(...)` are built on the same filter and behave the same way.

This is the single most damaging mistake you can make, because it produces a
project that compiles, runs, passes tests and scores `0hard/0soft` on every
input — a solver that does nothing, that looks like it works.

It bites hardest when an entity has **several** planning variables:

```java
@PlanningEntity
public class Assignment {
    @PlanningVariable(valueRangeProviderRefs = "employeeRange", allowsUnassigned = true)
    private Employee employee;

    @PlanningVariable(valueRangeProviderRefs = "equipmentRange", allowsUnassigned = true)
    private Equipment equipment;      // nothing in the score rewards assigning this
}
```

Nothing rewards assigning `equipment`, so the solver leaves it `null` on every
entity. Every entity therefore has an unassigned variable, `forEach(Assignment.class)`
returns an EMPTY stream, and every constraint in the provider matches nothing —
including the ones that have nothing to do with equipment. The failure is
self-reinforcing: the constraints that would push the solver toward assigning
`equipment` are themselves switched off by `equipment` being unassigned.

**The rule:**

1. Only mark a variable `allowsUnassigned = true` when the ProblemSpec genuinely
   allows that thing to be left unassigned. Do not add it defensively.
2. If ANY genuine variable on an entity is `allowsUnassigned = true`, then EVERY
   constraint rooted in that entity must use `forEachIncludingUnassigned(...)`
   instead of `forEach(...)`, with explicit null guards in the filters:

```java
// CORRECT for an entity that has an allowsUnassigned variable
factory.forEachIncludingUnassigned(Assignment.class)
        .filter(a -> a.getEmployee() != null && !a.getEmployee().hasSkill(a.getRequiredSkill()))
        .penalize(HardSoftScore.ONE_HARD)
        .asConstraint("Required skill");
```

3. Whenever a variable may be unassigned, write the constraint that makes the
   solver *want* to assign it (a medium-tier reward for assigning, or a penalty
   for leaving it null). An unassigned-capable variable with no score pressure
   is dead weight that disables your whole provider.
4. `forEachUniquePair(A.class, joiners...)` inherits the filter. Where the
   unfiltered pairs are needed, build the pair explicitly from
   `forEachIncludingUnassigned(A.class).join(A.class, ...)`.

## CRITICAL RULE: objectives are constraints, not comments

`ProblemSpec.constraints` tells you what is *allowed*. `ProblemSpec.objectives`
tells you what is *good*. A provider that implements only the first produces
some feasible answer and has no way to prefer a better one over a worse one.
Hard constraints alone cannot optimize: once the score is `0hard`, every
remaining arrangement looks identical to the solver.

Walk `ProblemSpec.objectives` the same way you walk `ProblemSpec.constraints`,
and give each one at least one `.reward(...)` or `.penalize(...)` at the medium
or soft level:

| Objective wording | Typical implementation |
|---|---|
| "schedule/assign as many X as possible" | reward each assigned entity, weighted by its importance, at the **medium** level |
| "weighted by urgency / priority / value" | reward with a match-weight function reading the weight field, not a flat `ONE_MEDIUM` |
| "meet targets / avoid lateness / stay near a due date" | penalize by the overshoot amount |
| "maximize utilization / minimize idle gaps" | penalize idle time or unused capacity per group |
| "balance / distribute fairly" | `groupBy` the actor, then penalize deviation from the target (`loadBalance` or squared deviation) |
| "prefer X, normally X, where possible X" | soft penalty on deviating from X — never a hard constraint |

Prefer weighted match functions over flat weights wherever the spec mentions
severity, priority, value, distance or lateness — the field exists in the domain
because the objective needs it:

```java
// Flat — throws away the priority the spec asked you to honour
.penalize(HardSoftScore.ONE_SOFT)

// Weighted — the objective actually discriminates between cases
.penalize(HardSoftScore.ONE_SOFT, task -> task.getSeverity() * task.getDaysLate())
```

**Dead-data check.** After writing the provider, list the fields you put on the
domain model and find the constraint that reads each one. A field carrying
priority, weight, severity, due date, target, entitlement, capacity or standard
deviation that no constraint reads is proof that an objective from the spec went
unimplemented. Either implement it or do not model the field.

## CRITICAL RULE: groupBy() collector arity must match the stream type

The collector type passed to `groupBy()` MUST match the current stream arity.
This is the single most frequent compilation error in generated projects.

| Current stream type   | Use these collector types                          |
|-----------------------|----------------------------------------------------|
| UniConstraintStream   | UniConstraintCollector (count, sum, min, max, toList, toConsecutiveSequences, ...) |
| BiConstraintStream    | BiConstraintCollector (countBi, toConsecutiveSequences(BiFunction, ToIntFunction), ...) |
| TriConstraintStream   | TriConstraintCollector (countTri, ...)             |
| QuadConstraintStream  | QuadConstraintCollector (countQuad, ...)           |

The arity of the stream is determined by how many joins you have done:
- `forEach(A.class)` → UniConstraintStream<A>
- `forEach(A.class).join(B.class, ...)` → BiConstraintStream<A, B>
- `BiStream.join(C.class, ...)` → TriConstraintStream<A, B, C>

**Wrong (will not compile):**
```java
// join gives BiStream, but count() is a UniCollector
factory.forEach(Shift.class)
       .join(Employee.class, equal(Shift::getEmployee, Function.identity()))
       .groupBy((shift, emp) -> emp, count())  // ERROR: count() is UniCollector
```

**Correct:**
```java
// BiStream → use countBi()
factory.forEach(Shift.class)
       .join(Employee.class, equal(Shift::getEmployee, Function.identity()))
       .groupBy((shift, emp) -> emp, countBi())
```

Available collectors by arity (import from `ConstraintCollectors.*`):
- Uni: `count()`, `sum(fn)`, `min(fn)`, `max(fn)`, `toList()`, `toConsecutiveSequences(ToIntFunction<A>)`, `loadBalance(fn, fn)`
- Bi: `countBi()`, `toConsecutiveSequences(BiFunction<A,B,Result_>, ToIntFunction<Result_>)`
- Tri: `countTri()`, ...
- Quad: `countQuad()`, ...

When in doubt: use `countBi()` on BiStreams and `count()` on UniStreams.

**groupBy maximum collector count:** The maximum overloads are:
- `groupBy(collector)` → BiStream
- `groupBy(collector1, collector2)` → TriStream
- `groupBy(keyFn, collector)` → BiStream
- `groupBy(keyFn, collector1, collector2)` → TriStream ← THIS IS THE MAXIMUM
- There is NO `groupBy(keyFn, col1, col2, col3)` — it does not exist. If you need 3 aggregations, restructure with multiple passes or use a custom domain method.

---

## CRITICAL RULE: toConsecutiveSequences — use the correct form for your stream arity

`toConsecutiveSequences` has TWO completely different forms and they are NOT interchangeable:

**Form 1 — UniCollector (1 argument):** Use this when grouping a UniStream.
```java
// forEach gives UniStream<Shift>. Group by employee, find consecutive days per employee.
factory.forEach(Shift.class)
       .groupBy(Shift::getEmployee,
                toConsecutiveSequences(shift -> (int) shift.getDate().toEpochDay()))
// Result: BiStream<Employee, SequenceChain<...>>
```
The single argument is `ToIntFunction<A>` — it maps each element of the group to an int index.

**Form 2 — BiCollector (2 arguments):** Use this when grouping a BiStream.
```java
// BiStream<Match, Team>. Group by team, find consecutive rounds per team.
factory.forEach(Match.class)
       .join(Team.class, equal(Match::getHomeTeam, Function.identity()))
       // BiStream<Match, Team>
       .groupBy((match, team) -> team,
                toConsecutiveSequences((match, team) -> match.getRound(), Round::getIndex))
// Result: BiStream<Team, SequenceChain<...>>
```
The first argument is `BiFunction<A,B,Result_>` and the second is `ToIntFunction<Result_>`.

**If your round/day index is already an int** (no intermediate Result_ object), use Integer boxing:
```java
toConsecutiveSequences((team, match) -> match.getRoundNumber(), Integer::intValue)
//  BiFunction<Team,Match,Integer>  ^                           ToIntFunction<Integer>  ^
```

**AVOID joining just to use toConsecutiveSequences.** If the sequence key (date, round number) is a field on the forEach entity, use Form 1 directly — no join needed:
```java
// WRONG — unnecessary join then BiCollector
factory.forEach(Match.class)
       .join(Team.class, ...)
       .groupBy((m, t) -> t, toConsecutiveSequences((m, t) -> m.getRoundNumber(), Integer::intValue))

// CORRECT — group directly, use UniCollector
factory.forEach(Match.class)
       .groupBy(Match::getHomeTeam,
                toConsecutiveSequences(m -> m.getRoundNumber()))
```

**NEVER pass a BiFunction to the 1-arg form:** `toConsecutiveSequences((a, b) -> ...)` with one argument will fail on a BiStream because the 1-arg form expects `ToIntFunction<A>` (not a BiFunction). Always supply BOTH arguments when on a BiStream.

## CRITICAL RULE: Joiners.equal() lambda arity must match the CURRENT stream

When you call `.join(X.class, equal(...))` or `.ifExists(X.class, equal(...))`:
- The FIRST argument to `equal()` is a function of ALL CURRENT STREAM ELEMENTS.
- The SECOND argument is a function of the JOINED class X.

| Current stream before join | First arg lambda type     | Second arg lambda type |
|----------------------------|---------------------------|------------------------|
| UniConstraintStream<A>     | `Function<A, P>`          | `Function<B, P>`       |
| BiConstraintStream<A,B>    | `BiFunction<A,B,P>`       | `Function<C, P>`       |
| TriConstraintStream<A,B,C> | `TriFunction<A,B,C,P>`    | `Function<D, P>`       |

**Wrong (will not compile on BiStream):**
```java
// biStream.join(C.class, equal(a -> a.getFoo(), c -> c.getFoo()))
// The first lambda only takes 'a' but the stream has TWO elements (a,b)
```
**Correct (on BiStream):**
```java
// biStream.join(C.class, equal((a, b) -> a.getFoo(), c -> c.getFoo()))
// The first lambda takes BOTH stream elements (a,b)
```

**This same arity rule applies to `ifExists` and `ifNotExists` joiners:**
- On a `UniConstraintStream<A>`, `.ifExists(B.class, joiner)` uses `BiJoiner<A, B>` — joiner lambda takes `(a, b)`.
- On a `BiConstraintStream<A,B>`, `.ifExists(C.class, joiner)` uses `TriJoiner<A, B, C>` — joiner lambda takes `(a, b, c)`.
- Passing a `BiJoiner` to a `BiConstraintStream.ifExists()` will NOT compile — the compiler expects a `TriJoiner`.

```java
// WRONG — BiStream.ifNotExists with BiJoiner (will not compile)
biStream.ifNotExists(Operation.class,
    equal(op1 -> op1.getId(), op2 -> op2.getPredecessorId()))  // BiJoiner — WRONG on BiStream

// CORRECT — BiStream.ifNotExists needs TriJoiner (lambda takes all 3 elements)
biStream.ifNotExists(Operation.class,
    equal((op1, op2) -> op1.getId(), op3 -> op3.getPredecessorId()))  // TriJoiner — correct
```

---

## CRITICAL RULE: Never join two grouped streams with dual-key-extractor `equal(...)`

There is NO `Joiners.equal(BiFunction, BiFunction)` overload. Trying to join two grouped `BiConstraintStream`s by giving each side its own key-extractor lambda will NOT compile — no amount of casting fixes it. This is a very common mistake when you want to compare two aggregates per key (e.g. "count of loans per volume > count of copies per volume").

```java
// WRONG — there is no equal(BiFunction, BiFunction) overload; will not compile
BiConstraintStream<Volume, Long> loansPerVolume =
    factory.forEach(Loan.class).groupBy(Loan::getVolume, count());
BiConstraintStream<Volume, Long> copiesPerVolume =
    factory.forEach(Copy.class).groupBy(Copy::getVolume, count());

loansPerVolume.join(copiesPerVolume,
    equal((vol, loanCount) -> vol, (vol, copyCount) -> vol))  // does not exist
```

**Correct pattern — anchor on the key class, join aggregates in via `ifExists`/`join` on that class:**

```java
// Compute both aggregates, then anchor on the shared key class
factory.forEach(Volume.class)
    .join(loansPerVolume, equal(v -> v, (vol, loanCount) -> vol))
    // Tri<Volume, Volume, Long>  — second Volume is redundant, drop via map if desired
    .join(copiesPerVolume, equal((v, vol, loanCount) -> v, (vol, copyCount) -> vol))
    // Quad<Volume, Volume, Long, Volume, Long> … getting ugly
```

**Better — push the join upstream of groupBy so you group a joined stream once:**

```java
// Join Loan to its Volume and Copy availability BEFORE grouping
factory.forEach(Loan.class)
    .filter(l -> l.getVolume() != null)
    .groupBy(Loan::getVolume, count())                              // Bi<Volume, Long loanCount>
    .join(Volume.class, equal((vol, loanCount) -> vol, v -> v))     // Tri<Volume, Long, Volume>
    .filter((vol, loanCount, v) -> loanCount > v.getCopyCount())    // Volume exposes the aggregate
    .penalize(HardSoftScore.ONE_HARD,
              (vol, loanCount, v) -> (int)(loanCount - v.getCopyCount()))
    .asConstraint("Inventory limit");
```

**Rule of thumb:** if you catch yourself writing two grouped streams and then trying to join them on a shared key, stop. Either (a) expose the second aggregate as a field/method on the key class (preferred — simpler and faster), or (b) anchor on the key class with `forEach(KeyClass)` and `join` each aggregate in separately. Never try `equal(BiFunction, BiFunction)`.

## CRITICAL RULE: penalize() match weight must be non-negative

The lambda or method reference passed as the match weight to `penalize()` MUST return a value >= 0. If the computation can produce a negative number (e.g., a subtraction), wrap it with `Math.max(0, value)`:

```java
// WRONG — can return negative if shiftCount < requiredCount
.penalize(HardSoftScore.ONE_HARD, (slot, count) -> slot.getRequired() - count)

// CORRECT — clamp to zero
.penalize(HardSoftScore.ONE_HARD, (slot, count) -> Math.max(0, slot.getRequired() - count))
```

Negative weights cause `ScoreCorruptionException` or incorrect scores.

---

## CRITICAL RULE: Never chain .filter().filter() — merge into one .filter()

Two consecutive `.filter()` calls on the same stream must always be combined into a single `.filter()` with `&&`. Chaining them is never necessary and produces ugly, unreadable code.

```java
// WRONG
.filter(ds -> ds.getAssignedAgent() != null)
.filter(ds -> ds.getAssignedAgent().getSkills().contains(ds.getRequiredSkill()))

// CORRECT
.filter(ds -> ds.getAssignedAgent() != null
        && ds.getAssignedAgent().getSkills().contains(ds.getRequiredSkill()))
```

This applies everywhere — on `forEach`, `join`, `groupBy` results, anywhere. If you find yourself writing `.filter(...).filter(...)`, stop and merge them.

---

## CRITICAL RULE: Never access planning entity data transitively in constraints (causes ScoreCorruptionException)

Timefold tracks score changes by knowing which entities a constraint depends on. If a constraint accesses entity B's data by going THROUGH entity A (a transitive reference), Timefold cannot detect that the score needs updating when B changes — causing `ScoreCorruptionException`.

**The rule:** If your constraint cares about data on entity X, iterate `forEach(X.class)` directly. Do NOT access X via a field on another entity.

```java
// WRONG — iterates Vehicle, then accesses visit data transitively through vehicle.visits
// Score is NOT re-evaluated when a visit's arrivalTime changes
factory.forEach(Vehicle.class)
       .filter(v -> v.getVisits().stream().anyMatch(visit -> visit.getArrivalTime().isAfter(visit.getDueTime())))
       .penalize(score)

// CORRECT — iterates Visit directly; score is re-evaluated when visit.arrivalTime changes
factory.forEach(Visit.class)
       .filter(visit -> visit.getArrivalTime() != null && visit.getArrivalTime().isAfter(visit.getDueTime()))
       .penalize(score)
```

The safe pattern for VRP time-window constraints: always `forEach(Visit.class)` and read shadow variables directly on the visit (`visit.getArrivalTime()`). Never stream through `vehicle.getVisits()` inside a constraint.

For `loadBalance` and `toConsecutiveSequences` constraints that group by a planning variable value (e.g., nurse), the planning variable itself (nurse) IS tracked — that is fine. What is NOT fine is calling methods on a third entity discovered through a reference that is not directly in the constraint stream.

---

## CRITICAL RULE: Use .complement() when penalizing "too few" assignments — forEach misses zero-count entities

`forEach(X.class)` only iterates over entities that have at least one match in the data. When you use `groupBy + count()` to find entities that have been assigned *fewer* than a minimum, entities with **zero** assignments never appear in the stream at all — so they are never penalized. This silently causes the solver to pile all assignments onto a single entity.

**The rule:** Any constraint of the form "penalize [fact] that has fewer than N [assignments]" MUST use `.complement()` after the `groupBy` to inject the zero-count facts back into the stream.

```java
// WRONG — students who borrowed 0 books are invisible; solver gives all books to one student
factory.forEach(BorrowedBook.class)
       .groupBy(BorrowedBook::getStudent, count())
       .filter((student, cnt) -> cnt < 3)
       .penalize(HardSoftScore.ONE_SOFT, (student, cnt) -> 3 - cnt)
       .asConstraint("Minimum books per student");

// CORRECT — complement() adds back students with 0 books, giving them count = 0
factory.forEach(BorrowedBook.class)
       .groupBy(BorrowedBook::getStudent, count())
       .complement(Student.class, student -> 0)   // inject missing students with count 0
       .filter((student, cnt) -> cnt < 3)
       .penalize(HardSoftScore.ONE_SOFT, (student, cnt) -> 3 - cnt)
       .asConstraint("Minimum books per student");
```

When to apply `.complement()`:
- The constraint penalizes a fact/value (Employee, Student, Vehicle…) for having **fewer than N** related entities assigned to it.
- The constraint uses `forEach(AssignedEntity).groupBy(AssignedEntity::getFact, count())` — and the count can legitimately be 0 for some facts.

When `.complement()` is NOT needed:
- You are penalizing **excess** (more than N): `count > N` — entities with 0 are already fine and don't need to appear.
- You are counting planning entities directly (e.g., `forEach(Shift.class)`) — every shift always appears.

The argument to `.complement(Fact.class, fact -> defaultValue)` must be the groupBy key type and a function returning the default count (almost always `0` / `-> 0`). The fact class (if it is a problem fact) must be registered as a `@ProblemFactCollectionProperty` on the solution so Timefold knows all instances.

---

## MANDATORY: Self-annotate stream arity before every groupBy / toConsecutiveSequences / ifExists call

Before writing any `.groupBy()`, `.toConsecutiveSequences()` collector, or `.ifExists()`/`.ifNotExists()` call,
you MUST add a single-line comment immediately above it stating the current stream type and the collector/joiner arity required. No exceptions.

Format: `// Stream: <Type> → <what you are about to call> needs <arity>`

Examples:
```java
// Stream: Uni<Shift> → groupBy needs UniCollector
.groupBy(Shift::getEmployee, toConsecutiveSequences(s -> (int) s.getDate().toEpochDay()))

// Stream: Bi<Match, Team> → groupBy needs key=BiFunction, collector=BiCollector
.groupBy((match, team) -> team,
         toConsecutiveSequences((match, team) -> match.getRound(), Round::getIndex))

// Stream: Uni<Shift> → ifExists needs BiJoiner<Shift, Availability>
.ifExists(Availability.class, equal(Shift::getEmployee, Availability::getEmployee))

// Stream: Bi<Operation, Operation> → ifNotExists needs TriJoiner<Op, Op, Dependency>
.ifNotExists(Dependency.class, equal((a, b) -> a.getId(), Dependency::getPredecessorId))
```

If you cannot immediately state the stream type, stop and trace back from `forEach()` counting each `.join()`. Only write the collector/joiner after you have written the comment.

## 1. Required Skill

**Level:** HARD — employee must have the skill required by the shift.

```java
Constraint requiredSkill(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .filter(shift -> !shift.getEmployee().getSkills()
                    .contains(shift.getRequiredSkill()))
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("Required skill");
}
```

## 2. No Overlapping Shifts

**Level:** HARD — one employee cannot work two shifts that overlap in time.

```java
Constraint noOverlappingShifts(ConstraintFactory factory) {
    return factory.forEachUniquePair(Shift.class,
                equal(Shift::getEmployee),
                overlapping(Shift::getStart, Shift::getEnd))
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("No overlapping shifts");
}
```

**Note:** `forEachUniquePair` avoids counting `(A,B)` and `(B,A)` as separate violations.

## 3. Employee Unavailability

**Level:** HARD — don't assign an employee to a shift on a day they're unavailable.

```java
Constraint unavailableEmployee(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .join(Availability.class,
                equal(Shift::getEmployee, Availability::getEmployee),
                equal(Shift::getDate, Availability::getDate))
            .filter((shift, avail) ->
                    avail.getType() == AvailabilityType.UNAVAILABLE)
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("Unavailable employee");
}
```

**Alternative using ifExists** (slightly faster — doesn't need the Availability in downstream):

```java
Constraint unavailableEmployee(ConstraintFactory factory) {
```

## 4. Minimum Rest Between Shifts

**Level:** HARD — enforce a minimum gap (e.g., 10 hours) between consecutive shifts of the same employee.

```java
private static final int MIN_REST_HOURS = 10;

Constraint minimumRestBetweenShifts(ConstraintFactory factory) {
    return factory.forEachUniquePair(Shift.class,
                equal(Shift::getEmployee))
            .filter((s1, s2) -> {
                Duration gap = gapBetween(s1, s2);
                return !gap.isNegative() && gap.toHours() < MIN_REST_HOURS;
            })
            .penalize(HardSoftScore.ONE_HARD,
                    (s1, s2) -> (int) (MIN_REST_HOURS - gapBetween(s1, s2).toHours()))
            .asConstraint("Minimum rest between shifts");
}

// Helper — returns the non-overlapping gap between two shifts
private static Duration gapBetween(Shift s1, Shift s2) {
    if (s1.getEnd().isBefore(s2.getStart())) {
        return Duration.between(s1.getEnd(), s2.getStart());
    } else if (s2.getEnd().isBefore(s1.getStart())) {
        return Duration.between(s2.getEnd(), s1.getStart());
    }
    return Duration.ZERO; // overlapping — handled by noOverlappingShifts
}
```

**Tip:** If shifts never overlap (enforced by the hard constraint above), you can simplify the gap calculation.

## 7. Maximum Consecutive Working Days

**Level:** HARD — no employee should work more than N consecutive calendar days.

```java
private static final int MAX_CONSECUTIVE_DAYS = 5;

Constraint maxConsecutiveWorkingDays(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .groupBy(Shift::getEmployee,
                    toConsecutiveSequences(shift -> shift.getDate().toEpochDay()))
            .flattenLast(SequenceChain::getConsecutiveSequences)
            .filter((employee, seq) -> seq.getCount() > MAX_CONSECUTIVE_DAYS)
            .penalize(HardSoftScore.ONE_HARD,
                    (employee, seq) -> seq.getCount() - MAX_CONSECUTIVE_DAYS)
            .asConstraint("Max consecutive working days");
}
```

**Requires import:**
```java
import ai.timefold.solver.core.api.score.stream.common.SequenceChain;
```

**How it works:** `toConsecutiveSequences()` groups shifts by employee and finds runs of consecutive epoch days. A sequence of 6 consecutive days when the max is 5 gets penalized by 1.

**Important:** This counts unique days. If an employee has two shifts on the same day, that day is counted only once because we group by `toEpochDay()`. If your employee might have multiple shifts per day and you want to count days (not shifts), first `groupBy(employee, date)` to deduplicate, then apply `toConsecutiveSequences`.

Pay attention to the invalid long to int conversions. For example if your toEpochDay() returns a long, and you put it into toConsecutiveSequences that reuires an int you will get the following error:
- Bad return type in lambda expression: long cannot be converted to int
with code:
.groupBy(ShiftAssignment::getNurse, toConsecutiveSequences(assignment -> assignment.getDay().getDate().toEpochDay()))

To fix it you can cast it later to int like so:
- toConsecutiveSequences(assignment -> (int) assignment.getDay().getDate().toEpochDay()))

This is a rule in general, do not put longs in places where ints are expected in the constraint streams provider as this will trigger compilation errors.

Also really important:
- If there is an Employee who has several shifts on the same toEpochDay, it will break the "toConsecutiveSequences(shift -> shift.getDate().toEpochDay()))". So there's also that to deal with, ensure it doesn't happen.

**Null safety requirement:** `toConsecutiveSequences()` will throw a `NullPointerException` at runtime if any grouping key is null. This happens when planning variables are unassigned (null) and you use the planning variable value as the grouping key. Always filter out unassigned entities BEFORE calling `toConsecutiveSequences()`:

```java
// WRONG — if shift.getEmployee() can be null, this throws at runtime
factory.forEach(Shift.class)
       .groupBy(Shift::getEmployee, toConsecutiveSequences(s -> (int) s.getDate().toEpochDay()))

// CORRECT — filter nulls first
factory.forEach(Shift.class)
       .filter(shift -> shift.getEmployee() != null)
       .groupBy(Shift::getEmployee, toConsecutiveSequences(s -> (int) s.getDate().toEpochDay()))
```

## 9. Fair Shift Distribution

**Level:** SOFT — distribute shifts evenly across all employees.

```java
Constraint fairShiftDistribution(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .groupBy(Shift::getEmployee, count())
            .complement(Employee.class, employee -> 0)
            .groupBy(loadBalance(
                    (employee, count) -> employee,
                    (employee, count) -> count))
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Fair shift distribution");
}
```

**Requires:**
```java
import ai.timefold.solver.core.api.score.stream.common.LoadBalance;
```

**Note:** `unfairness()` returns a `BigDecimal`. Multiply by 1000 and cast to `int` for use with `HardSoftScore`.

**Why complement?** Without `complement()`, employees with zero shifts are invisible to the stream. `complement(Employee.class, e -> 0)` adds them with count = 0, so the solver knows about them and can assign shifts fairly.

## 15. flattenLast — Unavailability Over a Set of Dates

**Level:** HARD — employee cannot be assigned to any shift that overlaps with any date in their unavailability set.

**When to use:** When an employee carries a `Set<LocalDate>` (or similar collection) of unavailable dates rather than a separate problem-fact class. `flattenLast` explodes the collection into individual stream elements.

```java
Constraint unavailableEmployee(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .join(Employee.class, equal(Shift::getEmployee, Function.identity()))
            .flattenLast(Employee::getUnavailableDates)
            // Now a TriConstraintStream<Shift, Employee, LocalDate>
            .filter(Shift::isOverlappingWithDate)
            .penalize(HardSoftScore.ONE_HARD, Shift::getOverlappingDurationInMinutes)
            .asConstraint("Unavailable employee");
}
```

**How it works:** After joining `Shift` with `Employee`, `flattenLast` replaces the last tuple element (Employee) with each individual element of `Employee::getUnavailableDates`. The stream becomes `Tri<Shift, Employee, LocalDate>`. The filter then checks whether the shift overlaps with that specific date.

**Note:** `flattenLast` can also be used on any grouped stream — e.g., after `toConsecutiveSequences()` use `flattenLast(SequenceChain::getConsecutiveSequences)` to iterate over individual sequences. The key rule: it always operates on the **last** element of the current tuple, which must be a `Collection` or `Iterable`.

**Same pattern for desiredDates / undesiredDates:**
```java
// Soft reward — employee prefers to work on desired dates
Constraint desiredDayForEmployee(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .join(Employee.class, equal(Shift::getEmployee, Function.identity()))
            .flattenLast(Employee::getDesiredDates)
            .filter(Shift::isOverlappingWithDate)
            .reward(HardSoftScore.ONE_SOFT, Shift::getOverlappingDurationInMinutes)
            .asConstraint("Desired day for employee");
}
```

## 17. Date-Window Constraint

**Level:** HARD — a job must not start before its earliest allowed start date, and must not end after its latest allowed end date. Penalize proportionally to how far outside the window.

**When to use:** Maintenance scheduling, project job scheduling, any problem with time-window feasibility requirements where the penalty scales with the violation magnitude.

```java
import static java.time.temporal.ChronoUnit.DAYS;

Constraint minStartDate(ConstraintFactory factory) {
    return factory.forEach(Job.class)
            .filter(job -> job.getMinStartDate() != null
                    && job.getStartDate().isBefore(job.getMinStartDate()))
            .penalize(HardSoftScore.ONE_HARD,
                    job -> (int) DAYS.between(job.getStartDate(), job.getMinStartDate()))
            .asConstraint("Min start date");
}

Constraint maxEndDate(ConstraintFactory factory) {
    return factory.forEach(Job.class)
            .filter(job -> job.getMaxEndDate() != null
                    && job.getEndDate().isAfter(job.getMaxEndDate()))
            .penalize(HardSoftScore.ONE_HARD,
                    job -> (int) DAYS.between(job.getMaxEndDate(), job.getEndDate()))
            .asConstraint("Max end date");
}
```

**Note:** `ChronoUnit.DAYS.between(a, b)` returns the number of days from `a` to `b` as a `long`. This naturally gives you the violation magnitude as the weight. Import `static java.time.temporal.ChronoUnit.DAYS` for concise usage. The same pattern works with `Duration.between(...).toMinutes()` for minute-level granularity.

## 18. Ideal-Date Soft Deviation

**Level:** SOFT — finishing earlier than ideal is wasteful; finishing later than ideal is risky. Apply asymmetric penalties scaled by the number of days of deviation.

**When to use:** Maintenance, project scheduling, or any domain where there is an optimal completion time and deviations in either direction have different costs.

```java
import static java.time.temporal.ChronoUnit.DAYS;

// Early completion — wasted effort (low penalty)
Constraint beforeIdealEndDate(ConstraintFactory factory) {
    return factory.forEach(Job.class)
            .filter(job -> job.getIdealEndDate() != null
                    && job.getEndDate().isBefore(job.getIdealEndDate()))
            .penalize(HardSoftScore.ofSoft(1),
                    job -> (int) DAYS.between(job.getEndDate(), job.getIdealEndDate()))
            .asConstraint("Before ideal end date");
}

// Late completion — risky (high penalty)
Constraint afterIdealEndDate(ConstraintFactory factory) {
    return factory.forEach(Job.class)
            .filter(job -> job.getIdealEndDate() != null
                    && job.getEndDate().isAfter(job.getIdealEndDate()))
            .penalize(HardSoftScore.ofSoft(1_000_000),
                    job -> (int) DAYS.between(job.getIdealEndDate(), job.getEndDate()))
            .asConstraint("After ideal end date");
}
```

**Tip:** Using vastly different weights (1 vs 1,000,000) models the business rule that late delivery is far worse than early delivery. Both constraints share the same score level but the solver will strongly prefer late avoidance over early avoidance.

## 19. Tag-Set Intersection Penalty

**Level:** SOFT — when two jobs/events that overlap in time share at least one common tag, penalize proportionally to the number of shared tags × the overlapping duration.

**When to use:** Any domain where items carry tags/categories and same-tag concurrency should be avoided (e.g., road maintenance in the same area, talks in the same theme track, jobs on the same equipment type).

```java
import java.util.Collections;
import java.util.HashSet;
import java.util.Set;
import static java.time.temporal.ChronoUnit.DAYS;

Constraint tagConflict(ConstraintFactory factory) {
    return factory.forEachUniquePair(Job.class,
                    overlapping(Job::getStartDate, Job::getEndDate),
                    filtering((job1, job2) -> !Collections.disjoint(
                            job1.getTags(), job2.getTags())))
            .penalize(HardSoftScore.ofSoft(1_000),
                    (job1, job2) -> {
                        Set<String> intersection = new HashSet<>(job1.getTags());
                        intersection.retainAll(job2.getTags());
                        long overlap = DAYS.between(
                                job1.getStartDate().isAfter(job2.getStartDate())
                                        ? job1.getStartDate() : job2.getStartDate(),
                                job1.getEndDate().isBefore(job2.getEndDate())
                                        ? job1.getEndDate() : job2.getEndDate());
                        return (int)(intersection.size() * overlap);
                    })
            .asConstraint("Tag conflict");
}
```

**Key points:**
- `Collections.disjoint(set1, set2)` returns `true` when there is NO overlap — so `!Collections.disjoint(...)` means "they share at least one element." Using it inside `filtering()` avoids evaluating the full intersection in the joiner, which is expensive.
- The weigher computes the actual intersection inside the lambda. This is acceptable since the `filtering` joiner already ensured there is at least one shared tag.
- This pattern composes the overlap check with a set-intersection computation — a common pattern for "tag/category conflict" constraints.

## 20. Consecutive Home/Away Match Limit (toConsecutiveSequences on BiStream)

**Level:** HARD — a team must not have more than N consecutive home (or away) matches in a row.

**When to use:** Sports scheduling or any domain where an entity cannot repeatedly hold the same role/location for too many consecutive periods.

```java
import ai.timefold.solver.core.api.score.stream.common.SequenceChain;
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.toConsecutiveSequences;

private static final int MAX_CONSECUTIVE_MATCHES = 4;

Constraint multipleConsecutiveHomeMatches(ConstraintFactory factory) {
    return factory.forEach(Match.class)
            .join(Team.class, equal(Match::getHomeTeam, Function.identity()))
            // BiConstraintStream<Match, Team>
            .groupBy((match, team) -> team,
                    toConsecutiveSequences((match, team) -> match.getRound(), Round::getIndex))
            // BiConstraintStream<Team, SequenceChain<Round, Match, Team>>
            .flattenLast(SequenceChain::getConsecutiveSequences)
            // BiConstraintStream<Team, ConsecutiveSequence<Round, Match, Team>>
            .filter((team, seq) -> seq.getCount() >= MAX_CONSECUTIVE_MATCHES)
            .penalize(HardSoftScore.ONE_HARD, (team, seq) -> seq.getCount())
            .asConstraint("4 or more consecutive home matches");
}
```

**How it works:**
1. Join `Match` with `Team` to create a Bi stream where we can group per team.
2. `toConsecutiveSequences((match, team) -> match.getRound(), Round::getIndex)` groups matches per team into runs of consecutive round indexes.
3. `flattenLast(SequenceChain::getConsecutiveSequences)` explodes the chain into individual consecutive sequences.
4. Filter sequences that are too long and penalize.

**Important:** `toConsecutiveSequences` requires the sequencing key to be an `int`. If your round/period identifier returns a `long`, cast it: `(int) round.getIndex()`. Duplicate sequencing keys per group will throw an exception — ensure uniqueness within each group.

**Requires:**
```java

import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.toConsecutiveSequences;
```

## 21. Symmetry-Breaking Repeat Constraint with ifExists

**Level:** HARD — the same pair of opponents must not play on back-to-back days (avoid immediate rematches).

**When to use:** Tournament/sports scheduling where rematches too soon are undesirable or forbidden. Also a general template for "entity A must not immediately follow entity B" constraints.

```java
Constraint repeatMatchOnNextDay(ConstraintFactory factory) {
    return factory.forEach(Match.class)
            .ifExists(Match.class,
                    equal(Match::getHomeTeam, Match::getAwayTeam),   // teams swapped
                    equal(Match::getAwayTeam, Match::getHomeTeam),
                    equal(match -> match.getRoundIndex() + 1, Match::getRoundIndex))
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("Repeat match on the next day");
}
```

**Pattern explanation:** The first `Match` in the stream is the "current" match. `ifExists` checks whether there is *any* match in the next round where the home and away teams are swapped. `equal(match -> match.getRoundIndex() + 1, Match::getRoundIndex)` is a shifted-equal joiner — left side adds 1 to current round index, right side is the next match's round index. This only triggers if a rematch exists exactly one round later.

**Note:** Use `lessThan(Match::getId)` or `lessThan(Match::getRoundIndex)` as a symmetry-breaking joiner whenever you match pairs of the same entity type without using `forEachUniquePair` — otherwise each pair is counted twice.

## 22. First/Last Assignment Boundary (ifNotExists with Ordering Joiner)

**Level:** SOFT — an employee's first flight should depart from their home airport; their last flight should arrive at their home airport. Use `ifNotExists` with ordering joiners to identify the first/last element in a sequence.

**When to use:** Any domain where sequence boundaries (first, last) carry constraints: routing, flight crew scheduling, task chains, etc.

```java
// First assignment: no earlier flight exists for this employee
Constraint firstAssignmentNotDepartingFromHome(ConstraintFactory factory) {
    return factory.forEach(Employee.class)
            .join(FlightAssignment.class,
                    equal(Function.identity(), FlightAssignment::getEmployee))
            // BiConstraintStream<Employee, FlightAssignment>
            .ifNotExists(FlightAssignment.class,
                    equal((emp, fa) -> emp, FlightAssignment::getEmployee),
                    greaterThan((emp, fa) -> fa.getDepartureUTCDateTime(),
                            FlightAssignment::getDepartureUTCDateTime))
            // Only the earliest flight per employee survives
            .filter((employee, fa) -> !employee.getHomeAirport()
                    .equals(fa.getFlight().getDepartureAirport()))
            .penalize(HardSoftScore.ofSoft(1000))
            .asConstraint("First assignment not departing from home");
}

// Last assignment: no later flight exists for this employee
Constraint lastAssignmentNotArrivingAtHome(ConstraintFactory factory) {
    return factory.forEach(Employee.class)
            .join(FlightAssignment.class,
                    equal(Function.identity(), FlightAssignment::getEmployee))
            .ifNotExists(FlightAssignment.class,
                    equal((emp, fa) -> emp, FlightAssignment::getEmployee),
                    lessThan((emp, fa) -> fa.getDepartureUTCDateTime(),
                            FlightAssignment::getDepartureUTCDateTime))
            // Only the latest flight per employee survives
            .filter((employee, fa) -> !employee.getHomeAirport()
                    .equals(fa.getFlight().getArrivalAirport()))
            .penalize(HardSoftScore.ofSoft(1000))
            .asConstraint("Last assignment not arriving at home");
}
```

**How it works:** `ifNotExists` on a `BiConstraintStream<Employee, FlightAssignment>` takes a third class and up to 4 joiners. The `greaterThan` joiner on a Bi stream checks whether there exists *any* assignment for the same employee that departs **earlier** than the current one. If no such earlier assignment exists, the current tuple is the first. The `.filter()` then checks the boundary condition.

**Key:** When using `ifNotExists` on a Bi stream, the joiner lambdas have arity-2 for the "left side" (they receive both elements of the existing Bi tuple) and arity-1 for the "right side" (they receive the new class).

## 23. Three-Way Join for Attendance Conflict

**Level:** HARD — a person required at meeting A must not be simultaneously required at meeting B. Requires joining attendance records with their assignments.

**When to use:** Any domain with an intermediate "attendance" or "assignment" fact that links people to events, where you need to check time overlap between two events via those facts.

```java
Constraint requiredAttendanceConflict(ConstraintFactory factory) {
    return factory.forEachUniquePair(RequiredAttendance.class,
                    equal(RequiredAttendance::getPerson))
            // BiStream: two attendance records for the same person, different meetings
            .join(MeetingAssignment.class,
                    equal((left, right) -> left.getMeeting(), MeetingAssignment::getMeeting))
            // TriStream: left attendance, right attendance, left meeting assignment
            .join(MeetingAssignment.class,
                    equal((left, right, leftAssignment) -> right.getMeeting(),
                            MeetingAssignment::getMeeting),
                    overlapping(
                            (left, right, leftAssignment) -> leftAssignment.getGrainIndex(),
                            (left, right, leftAssignment) -> leftAssignment.getLastTimeGrainIndex() + 1,
                            MeetingAssignment::getGrainIndex,
                            assignment -> assignment.getLastTimeGrainIndex() + 1))
            // QuadStream: fully joined, filter overlapping
            .penalize(HardSoftScore.ONE_HARD,
                    (left, right, leftAssignment, rightAssignment) ->
                            rightAssignment.calculateOverlap(leftAssignment))
            .asConstraint("Required attendance conflict");
}
```

**Key technique:** As you chain joins, the lambda arity grows: the first `.join()` gets a `BiFunction` for the left side (receiving both Bi elements) plus a `Function` for the right class. The second `.join()` gets a `TriFunction` for the left side (receiving all 3 current elements) plus a `Function` for the new class. Always count your arities carefully.

## 24. Four-Way Join for Cross-Entity Time Overlap

**Level:** SOFT — similar to §23 but using `forEachIncludingUnassigned` substreams with pre-filtering. Demonstrates joining a pre-filtered stream as a substream argument.

**When to use:** When you need to join against a filtered version of a class (not all instances) and must avoid including unassigned entities in the overlap logic.

```java
Constraint preferredAttendanceConflict(ConstraintFactory factory) {
    // Substream: only assignments that have been given a starting time grain
    var assignedMeetings = factory.forEachIncludingUnassigned(MeetingAssignment.class)
            .filter(a -> a.getStartingTimeGrain() != null);

    return factory.forEachUniquePair(PreferredAttendance.class,
                    equal(PreferredAttendance::getPerson))
            .join(assignedMeetings,
                    equal((left, right) -> left.getMeeting(), MeetingAssignment::getMeeting))
            .join(assignedMeetings,
                    equal((left, right, leftA) -> right.getMeeting(), MeetingAssignment::getMeeting),
                    overlapping(
                            (left, right, leftA) -> leftA.getGrainIndex(),
                            (left, right, leftA) -> leftA.getLastTimeGrainIndex() + 1,
                            MeetingAssignment::getGrainIndex,
                            a -> a.getLastTimeGrainIndex() + 1))
            .penalize(HardSoftScore.ONE_SOFT,
                    (left, right, leftA, rightA) -> rightA.calculateOverlap(leftA))
            .asConstraint("Preferred attendance conflict");
}
```

**Key technique:** You can pass a pre-built `ConstraintStream` (stored in a variable) as the argument to `join()` instead of a bare class. This lets you filter or transform one side of the join before joining. This is the only way to join a pre-filtered stream without relying on `Joiners.filtering()` for every tuple.

## 25. countBi / countDistinct in groupBy

**Level:** HARD/SOFT — count the number of distinct values of a field within a group, or count pairs in a Bi stream.

**When to use:**
- `countBi()` when you are counting elements in a `BiConstraintStream` (i.e., after a join). Plain `count()` will not compile on a Bi stream.
- `countDistinct()` when you want the number of *unique* values within a group (e.g., how many distinct trolleys does an order span?).

```java
// countBi — counting after a join
// "How many employees are assigned to each shift slot?"
Constraint minimumStaffing(ConstraintFactory factory) {
    return factory.forEach(ShiftSlot.class)
            .join(Shift.class,
                    equal(ShiftSlot::getStart, Shift::getStart),
                    equal(ShiftSlot::getSkill, Shift::getRequiredSkill))
            .groupBy((slot, shift) -> slot, countBi())
            .filter((slot, count) -> count < slot.getRequiredCount())
            .penalize(HardSoftScore.ONE_HARD,
                    (slot, count) -> slot.getRequiredCount() - count)
            .asConstraint("Minimum staffing per slot");
}

// countDistinct — distinct values in a group
// "Penalize orders that are split across more than one trolley"
Constraint minimizeOrderSplit(ConstraintFactory factory) {
    return factory.forEach(PickTask.class)
            .groupBy(pick -> pick.getOrderItem().getOrder(),
                    countDistinct(PickTask::getTrolley))
            .filter((order, trolleyCount) -> trolleyCount > 1)
            .penalize(HardSoftScore.ONE_SOFT,
                    (order, trolleyCount) -> trolleyCount * 1000)
            .asConstraint("Minimize order split by trolley");
}
```

**Imports:**
```java
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.countBi;
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.countDistinct;
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.countDistinctLong;
```

**Rule:** Use `count()` on `UniConstraintStream`, `countBi()` on `BiConstraintStream`, `countTri()` on `TriConstraintStream`, `countQuad()` on `QuadConstraintStream`. Mismatching arity causes a compile error.

## 26. expand() — Cache a Computed Value

**When to use:** When you need to call an expensive (or non-trivial) method on an entity multiple times in the same constraint — or when the result is used both in a filter and in a weigher. `expand()` computes it once and adds it to the tuple.

```java
// Without expand — computes missingSpeakerRequiredTimeslotTagCount() twice
factory.forEach(Talk.class)
    .filter(talk -> talk.missingSpeakerRequiredTimeslotTagCount() > 0)
    .penalize(HardSoftScore.ofHard(1),
            talk -> talk.missingSpeakerRequiredTimeslotTagCount() * talk.getDurationInMinutes())
    .asConstraint("Speaker required timeslot tags");

// With expand — computes once, reuses in filter and weigher
factory.forEach(Talk.class)
    .expand(Talk::missingSpeakerRequiredTimeslotTagCount)
    // Now a BiConstraintStream<Talk, Integer>
    .filter((talk, missingCount) -> missingCount > 0)
    .penalize(HardSoftScore.ofHard(1),
            (talk, missingCount) -> missingCount * talk.getDurationInMinutes())
    .indictWith((talk, missingCount) -> Collections.singleton(talk))
    .asConstraint("Speaker required timeslot tags");
```

**Notes:**
- `expand()` adds a new element to the tuple, increasing cardinality: `Uni → Bi`, `Bi → Tri`, etc. Maximum cardinality is 4, so you can call `expand()` at most 3 times on a `UniConstraintStream`.
- The expanded value is computed once per entity instance and reused throughout the constraint. This is a performance optimization for costly domain method calls.
- You can call `indictWith()` after `expand()` to control which objects are blamed for the violation. In the example above, only the `Talk` is indicted (not the computed integer). `indictWith` is optional and is purely for score explanation / UI purposes.

## 27. compose() Collector — Derive a Value from min + max

**When to use:** When you need to compute a single derived metric that requires two (or more) different collector results — for example, computing the span (max − min) of timestamps per group.

```java
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.compose;
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.min;
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.max;
import java.time.LocalDate;
import java.time.temporal.ChronoUnit;

// Penalize speakers whose talks span more than 1 day of the conference
Constraint speakerMakespan(ConstraintFactory factory) {
    return factory.forEach(Speaker.class)
            .join(Talk.class,
                    filtering((speaker, talk) -> talk.hasSpeaker(speaker)))
            .groupBy(
                    (speaker, talk) -> speaker,
                    compose(
                        min((Speaker speaker, Talk talk) -> talk,
                                talk -> talk.getTimeslot().getStartDateTime()),
                        max((Speaker speaker, Talk talk) -> talk,
                                talk -> talk.getTimeslot().getStartDateTime()),
                        (firstTalk, lastTalk) -> {
                            LocalDate first = firstTalk.getTimeslot().getStartDateTime().toLocalDate();
                            LocalDate last  = lastTalk.getTimeslot().getStartDateTime().toLocalDate();
                            return (int) Math.abs(ChronoUnit.DAYS.between(first, last));
                        }))
            // BiConstraintStream<Speaker, Integer> — days between first and last talk
            .filter((speaker, daySpan) -> daySpan > 1)
            .penalize(HardSoftScore.ofSoft(20),
                    (speaker, daySpan) -> (daySpan - 1) * 8 * 60)
            .asConstraint("Speaker makespan");
}
```

**How it works:**
- `compose(collector1, collector2, mergerFn)` runs both collectors in parallel over the same grouped elements, then passes their results to `mergerFn` to produce a single value.
- `min((BiFunction) selector, Comparable keyExtractor)` and `max(...)` on a `BiConstraintStream` take a two-argument selector that maps `(A, B) -> T` and then extract a `Comparable` from `T` for ordering.
- The merged result replaces both collectors in the output: the `groupBy` here produces a `BiConstraintStream<Speaker, Integer>` (1 group key + 1 composed result).

**Note:** `compose` supports 2 to 4 collectors. It avoids having to do multiple separate `groupBy` operations to compute different aggregates.

## 28. Multi-Step groupBy Pipeline (Chained Aggregation)

**When to use:** When the desired aggregation cannot be expressed in a single `groupBy` — for example, computing "total buckets required per trolley" requires first computing "required buckets per order per trolley", then summing across orders per trolley.

```java
// Step 1: Compute total volume per (trolley, order)
// Step 2: Compute required buckets per (trolley, order)
// Step 3: Sum required buckets per trolley
// Step 4: Penalize if trolley is over capacity

Constraint requiredNumberOfBuckets(ConstraintFactory factory) {
    return factory.forEach(PickTask.class)
            // Step 1: total item volume per (trolley, order)
            .groupBy(PickTask::getTrolley,
                     pick -> pick.getOrderItem().getOrder(),
                     sum(pick -> pick.getOrderItem().getVolume()))
            // TriConstraintStream<Trolley, Order, Integer>

            // Step 2: convert volume to bucket count per (trolley, order)
            .groupBy((trolley, order, totalVolume) -> trolley,
                     (trolley, order, totalVolume) -> order,
                     sum((trolley, order, totalVolume) ->
                             calculateRequiredBuckets(totalVolume, trolley.getBucketCapacity())))
            // TriConstraintStream<Trolley, Order, Integer> — buckets needed per order

            // Step 3: sum required buckets across all orders for each trolley
            .groupBy((trolley, order, buckets) -> trolley,
                     sum((trolley, order, buckets) -> buckets))
            // BiConstraintStream<Trolley, Integer> — total buckets needed per trolley

            // Step 4: penalize over-capacity
            .filter((trolley, totalBuckets) -> trolley.getBucketCount() < totalBuckets)
            .penalize(HardSoftScore.ONE_HARD,
                    (trolley, totalBuckets) -> totalBuckets - trolley.getBucketCount())
            .asConstraint("Required number of buckets");
}
```

**Key points:**
- Each `groupBy` call resets the stream to the group-key + collector-result cardinality. You are NOT accumulating state from previous `groupBy`s; each one starts fresh from the current tuple structure.
- Inside a `groupBy` on a `TriConstraintStream`, the key/collector lambdas receive all three elements. Explicitly name them to avoid confusion: `(trolley, order, totalVolume) -> trolley`.
- This pattern is unusual. Only use chained `groupBy` when a single-step aggregation is genuinely insufficient. In most problems, a single `groupBy` with one key and one collector is sufficient.

## 29. loadBalance Shorthand (1-arg, no complement)

**When to use:** When all candidate entities are always present in the stream (no unassigned possibility) and you simply want to distribute assignments evenly. The 1-argument form of `loadBalance` is a direct shorthand that avoids the `complement` step.

```java
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.loadBalance;

// Distribute team assignments evenly across all teams
Constraint fairAssignmentCountPerTeam(ConstraintFactory factory) {
    return factory.forEach(TeamAssignment.class)
            .groupBy(loadBalance(TeamAssignment::getTeam))
            // UniConstraintStream<LoadBalance>
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Fair assignment count per team");
}
```

**Requires:**
```java
import ai.timefold.solver.core.api.score.stream.common.LoadBalance;
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.loadBalance;
```

Use the shorthand form here only when every "load recipient" is guaranteed to appear at least once in the stream (e.g., each team always has at least one assignment).

## 30. loadBalance on BiConstraintStream (Pair Fairness)

**When to use:** When you want to balance the number of times each *pair* of entities confronts or interacts — for example, ensuring each pair of teams plays against each other roughly equally often in a tournament.

```java
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.loadBalance;

Constraint evenlyConfrontationCount(ConstraintFactory factory) {
    return factory.forEach(TeamAssignment.class)
            .join(TeamAssignment.class,
                    equal(TeamAssignment::getDay),
                    lessThan(a -> a.getTeam().getId()))
            // BiConstraintStream<TeamAssignment, TeamAssignment> — pairs on the same day
            .groupBy(loadBalance(
                    (a, b) -> new Pair<>(a.getTeam(), b.getTeam())))
            // UniConstraintStream<LoadBalance>
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Evenly confrontation count");
}

public record Pair<A, B>(A key, B value) {}
```

**Key points:**
- `loadBalance` on a `BiConstraintStream` takes a `BiFunction` that maps both elements to the "load recipient" key. Here each pair `(teamA, teamB)` is the key.
- `lessThan(a -> a.getTeam().getId())` is used as a symmetry-breaking joiner so that `(teamA, teamB)` and `(teamB, teamA)` are counted as a single pair (avoids double-counting). This replaces the need for `forEachUniquePair`.
- The `Pair` record is a simple holder. Use any `record` or class with proper `equals/hashCode` as the key.
- **Note:** `unfairness()` returns a `BigDecimal`. Multiply by 1000 and cast to `int` for use with `HardSoftScore`.

## 31. Reward Pattern (Diversity Bonus)

**When to use:** When you want to reward — rather than penalize — the solver for achieving a desirable state. `reward()` increases the score, which the solver maximizes.

```java
// Reward having talks of different audience types in the same timeslot
Constraint audienceTypeDiversity(ConstraintFactory factory) {
    return factory.forEachUniquePair(Talk.class,
                    equal(Talk::getTimeslot),
                    filtering((t1, t2) -> t2.overlappingAudienceTypeCount(t1) > 0))
            .reward(HardSoftScore.ofSoft(1),
                    (t1, t2) -> t1.overlappingAudienceTypeCount(t2)
                            * t1.getTimeslot().getDurationInMinutes())
            .asConstraint("Audience type diversity");
}

// Reward talks in the same timeslot having different languages
Constraint languageDiversity(ConstraintFactory factory) {
    return factory.forEachUniquePair(Talk.class,
                    equal(Talk::getTimeslot))
            .filter((t1, t2) -> !t1.getLanguage().equals(t2.getLanguage()))
            .reward(HardSoftScore.ofSoft(10),
                    (t1, t2) -> t1.getTimeslot().getDurationInMinutes())
            .asConstraint("Language diversity");
}
```

**Notes:**
- `reward()` has the same signature variants as `penalize()`: static weight and dynamic weight with a weigher function (returning `int`).
- Reward constraints increase the soft score, so the solver will seek solutions where more reward constraints are satisfied, all else being equal.
- A diversity reward and a conflict penalty often appear together in scheduling: the reward pulls items apart into different slots, while a conflict penalty pushes them apart even harder when it's a hard requirement.

## 32. Squared Penalty for Makespan Minimization

**When to use:** When you want the solver to strongly prefer solutions that finish early overall — penalizing late endings super-linearly so that one very long job is worse than two medium ones. The squared penalty creates a convex cost that the solver minimizes more aggressively.

```java
// Penalize total makespan of a line as the square of its duration in minutes
Constraint minimizeMakespan(ConstraintFactory factory) {
    return factory.forEach(Job.class)
            .filter(job -> job.getLine() != null && job.getNextJob() == null)
            // Only the last job in each line's chain contributes
            .penalize(HardSoftScore.ONE_SOFT, job -> {
                long minutes = Duration.between(
                        job.getLine().getStartDateTime(), job.getEndDateTime()).toMinutes();
                return (int)(minutes * minutes);
            })
            .asConstraint("Minimize makespan");
}

// Penalize employee makespan as end_time^2 to prefer even load
Constraint minimizeMakespanSquared(ConstraintFactory factory) {
    return factory.forEach(Employee.class)
            .penalize(HardSoftScore.ONE_SOFT,
                    employee -> employee.getEndTime() * employee.getEndTime())
            .asConstraint("Minimize makespan squared");
}
```

**Why squared?** Linear `penalize(..., t -> t)` gives equal preference to "finish at time 10" vs "two jobs finishing at times 5 and 5" (same total). Squaring makes `10² = 100` much worse than `5² + 5² = 50`, so the solver strongly prefers finishing earlier and distributing load evenly.

**Note:** If the squared value could overflow `int` (approximately 46,000 minutes squared), scale the input down first (e.g., use hours instead of minutes) and cast to `int`.

## 35. penalize / reward Variants

Since the project always uses `HardSoftScore`, always use `.penalize()` and `.reward()` (not `penalizeLong` or `penalizeBigDecimal`). Weighers must return `int`.

If a calculation naturally produces a `long` (e.g., `ChronoUnit.DAYS.between(...)`, `Duration.toMinutes()`), cast to `int`:

```java
// Cast long result to int
.penalize(HardSoftScore.ONE_HARD,
        (j1, j2) -> (int) ChronoUnit.DAYS.between(j1.getStartDate(), j2.getEndDate()))
.asConstraint("Crew conflict");

// Reward variant
.reward(HardSoftScore.ONE_SOFT, visit -> visit.getServiceDurationMinutes())
.asConstraint("Preferred visit duration");
```

**Score type ↔ penalize method:**

| Score type | penalize method | weigher return type |
|---|---|---|
| `HardSoftScore` | `penalize` | `int` |

**Critical:** Always use `penalize` (not `penalizeLong`/`penalizeBigDecimal`) with `HardSoftScore`. If a value could overflow `int`, scale it down (e.g., use minutes instead of seconds, days instead of minutes).

## 36. ifExists / ifNotExists on Bi and Tri Streams

**When to use:** After a join (i.e., on a `BiConstraintStream` or `TriConstraintStream`), use `ifExists` or `ifNotExists` to further filter based on the existence of a third (or fourth) entity without increasing cardinality.

```java
// ifExists on a UniConstraintStream — crowd control:
// penalize talks where more than one talk with crowd risk is in the same timeslot
Constraint crowdControl(ConstraintFactory factory) {
    return factory.forEach(Talk.class)
            .filter(talk -> talk.getCrowdControlRisk() > 0)
            .join(factory.forEach(Talk.class)
                    .filter(talk -> talk.getCrowdControlRisk() > 0),
                    equal(Talk::getTimeslot))
            .filter((t1, t2) -> !Objects.equals(t1, t2))
            .groupBy((t1, t2) -> t1, countBi())
            .filter((talk, count) -> count != 1)
            .penalize(HardSoftScore.ofHard(1), (talk, count) -> talk.getDurationInMinutes())
            .asConstraint("Crowd control");
}

// ifNotExists on a BiConstraintStream — with ordering joiner
// (see §22 for the full first/last boundary pattern)
// The key rule: on a Bi stream, ifExists/ifNotExists joiners receive a BiFunction for the
// left side (both existing elements) and a Function for the right class.
factory.forEach(Employee.class)
    .join(FlightAssignment.class,
            equal(Function.identity(), FlightAssignment::getEmployee))
    .ifNotExists(FlightAssignment.class,
            equal((emp, fa) -> emp, FlightAssignment::getEmployee),
            greaterThan((emp, fa) -> fa.getDepartureUTCDateTime(),
                    FlightAssignment::getDepartureUTCDateTime))
    // Remaining: the earliest flight per employee
```

**ifExists with a problem-fact class (config object):**
```java
// ifExists with a singleton config object to look up a setting
Constraint consecutiveTalksPause(ConstraintFactory factory) {
    return factory.forEachUniquePair(Talk.class,
                    filtering((t1, t2) -> t2.hasMutualSpeaker(t1)))
            .ifExists(ConferenceConstraintProperties.class,
                    filtering((t1, t2, config) ->
                            !t1.getTimeslot().pauseExists(t2.getTimeslot(),
                                    config.getMinimumConsecutiveTalksPauseInMinutes())))
            .penalize(HardSoftScore.ofHard(1), Talk::combinedDurationInMinutes)
            .asConstraint("Consecutive talks pause");
}
```

**Note:** `ifExists(Class, joiners...)` on a `BiConstraintStream` produces the same `BiConstraintStream` — cardinality does NOT increase. The joiner lambdas for the "left side" now have arity 2 (they receive both Bi elements). Always count the arity of your lambdas carefully when working on higher-cardinality streams.

## 37. Four-Argument overlapping Joiner

**When to use:** When the two intervals being checked for overlap come from different sources in a Bi/Tri stream, so each side's start and end must be computed from different tuple elements.

```java
// In a TriConstraintStream<LeftAttendance, RightAttendance, LeftAssignment>
// joining a fourth stream MeetingAssignment, checking time overlap with leftAssignment:
.join(MeetingAssignment.class,
        equal((left, right, leftA) -> right.getMeeting(), MeetingAssignment::getMeeting),
        overlapping(
                (left, right, leftA) -> leftA.getGrainIndex(),
                (left, right, leftA) -> leftA.getLastTimeGrainIndex() + 1,
                MeetingAssignment::getGrainIndex,
                assignment -> assignment.getLastTimeGrainIndex() + 1))
```

**Signature:**
```java
overlapping(
    TriFunction<A, B, C, T> startExtrA,   // start of left interval
    TriFunction<A, B, C, T> endExtrA,     // end of left interval
    Function<D, T> startExtrB,            // start of right interval
    Function<D, T> endExtrB               // end of right interval
)
```

**Rules:**
- The 2-argument shorthand `overlapping(startFn, endFn)` is used with `forEachUniquePair` or when both sides use the same class with the same getters.
- The 4-argument form is used in joins where the two intervals are derived from different (possibly composite) parts of the stream.
- The start/end extractor arity must match the cardinality of the stream at the point of the join.

## 38. max() Collector for Global Makespan

**When to use:** When you need to find the single maximum (or minimum) value across all entities in a group and penalize based on that extremum. Common in project scheduling where the overall completion time is the makespan.

```java
import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.max;

// Penalize the overall project makespan (end date of the last SINK job)
Constraint totalMakespan(ConstraintFactory factory) {
    return factory.forEach(Allocation.class)
            .filter(a -> a.getJobType() == JobType.SINK && a.getEndDate() != null)
            .groupBy(max(Allocation::getEndDate))
            // UniConstraintStream<Integer> — the single maximum end date
            .penalize(HardSoftScore.ONE_SOFT, maxEndDate -> maxEndDate)
            .asConstraint("Total makespan");
}
```

**Variants:**
```java
// min — earliest start across all entities
.groupBy(min(Allocation::getStartDate))

// max on a BiConstraintStream — with mapping function
max((Speaker speaker, Talk talk) -> talk,
     talk -> talk.getTimeslot().getStartDateTime())
// Returns the Talk whose timeslot starts latest
```

**Note:** `max()` and `min()` return a single value of the mapped type. The result is `null` if the group is empty. After `groupBy(max(...))`, you have a `UniConstraintStream<T>` where `T` is the type returned by the extractor function (not the original entity). If you need the maximum entity object itself, supply an identity mapper: `max((Talk t) -> t, talk -> talk.getTimeslot().getStartDateTime())`.

## 39. Minimize Total Distance (Chain-Model Pattern)

**When to use:** In routing or order-picking problems where entities form a chain (each entity knows its predecessor) and you want to minimize the total travel distance.

```java
// Penalize the travel distance from each visit/task to its predecessor
// (works with a linked-list "previous" shadow variable or explicit chain)
Constraint minimizeDistanceFromPrevious(ConstraintFactory factory) {
    return factory.forEach(PickTask.class)
            .penalize(HardSoftScore.ONE_SOFT,
                    pick -> {
                        var previousLocation = pick.getPreviousPickTask() != null
                                ? pick.getPreviousPickTask().getLocation()
                                : pick.getTrolley().getLocation();
                        return (int) calculateDistance(previousLocation, pick.getLocation());
                    })
            .asConstraint("Minimize distance from previous pick task");
}

// Penalize the return distance for the last task in each chain
Constraint minimizeReturnDistance(ConstraintFactory factory) {
    return factory.forEach(PickTask.class)
            .filter(PickTask::isLast)
            .penalize(HardSoftScore.ONE_SOFT,
                    pick -> (int) calculateDistance(pick.getLocation(), pick.getTrolley().getLocation()))
            .asConstraint("Minimize return distance");
}
```

**Notes:**
- In chain models, shadow variables (`@ShadowVariable` or `@PreviousElementShadowVariable`) compute `previousPickTask` and `isLast()` automatically as the solver changes the `@PlanningListVariable`. The constraint does not need to join on the chain — it simply reads shadow variable values.
- This pattern is also used in vehicle routing: `forEach(Vehicle.class).penalize(..., v -> (int)v.getTotalDrivingTimeSeconds())` where the total is computed as a shadow variable over the vehicle's visit list.
- Always ensure the distance calculation is consistent with how the shadow variables are computed.

## Vehicle Routing Problem (VRP) Constraints

VRP problems use a `@PlanningListVariable` on the `Vehicle` (a list of `Visit` objects). Shadow variables on `Vehicle` and `Visit` pre-compute aggregates (total demand, total driving time, arrival times) so constraints stay simple. The canonical score type is `HardSoftScore`: hard = feasibility, soft = minimize travel.

**Imports assumed for this section:**
```java
import ai.timefold.solver.core.api.score.buildin.hardsoft.HardSoftScore;
import ai.timefold.solver.core.api.score.stream.Constraint;
import ai.timefold.solver.core.api.score.stream.ConstraintFactory;
import ai.timefold.solver.core.api.score.stream.ConstraintProvider;
```

**VRP domain sketch (adapt getters to your model):**
```java
// @PlanningSolution
class VehicleRoutePlan { List<Vehicle> vehicles; List<Visit> visits; HardSoftScore score; }

// Has @PlanningListVariable List<Visit> visits  (the route)
// Shadow variables compute: getTotalDemand(), getTotalDrivingTimeSeconds()
class Vehicle { long getCapacity(); long getTotalDemand(); long getTotalDrivingTimeSeconds(); }

// @PlanningEntity (via @InverseRelationShadowVariable back to Vehicle)
// Shadow variables compute: getArrivalTime(), isServiceFinishedAfterMaxEndTime(), getServiceFinishedDelayInMinutes()
class Visit { LocalDateTime getMinStartTime(); LocalDateTime getMaxEndTime(); Duration getServiceDuration();
              Vehicle getVehicle(); boolean isServiceFinishedAfterMaxEndTime(); long getServiceFinishedDelayInMinutes(); }
```

## 40. VRP — forEachIncludingUnassigned

**Level:** SOFT — penalize every visit that is not assigned to any vehicle.

**When to use:** Any overconstrained routing problem where the fleet may be too small to serve all visits. Use a large soft weight so the solver strongly prefers assigning visits over skipping them.

```java
Constraint maximizeVisitsAssigned(ConstraintFactory factory) {
    return factory.forEachIncludingUnassigned(Visit.class)
            .filter(visit -> visit.getVehicle() == null)
            .penalize(HardSoftScore.ofSoft(1000),
                    visit -> (int) visit.getServiceDuration().toMinutes())
            .asConstraint("Maximize visits assigned");
}
```

**Notes:**
- `forEach` silently skips unassigned entities (those with a `null` planning variable). **`forEachIncludingUnassigned`** includes them, which is the only way to penalize or reward the mere fact of being unassigned.
- Use a large soft weight (e.g., `ofSoft(1000)`) so the solver strongly prefers assigning visits over skipping them.
- This is the standard pattern for overconstrained VRP. Use it whenever not all demand can feasibly be served. Without it the solver may produce solutions with silently unserved visits.
- `forEachIncludingUnassigned` exists for `@PlanningListVariable` and `@PlanningVariable` alike. On a `@PlanningVariable`, the null check is `entity.getPlanningVar() == null`; on a list variable, the check is typically done on the inverse side (`visit.getVehicle() == null`).

---

## 41. VRP — Vehicle-Centric Shadow-Aggregate Constraint

**Level:** HARD (capacity) and SOFT (travel time) — read shadow-variable aggregates directly off the `Vehicle` entity instead of joining across visits.

**When to use:** Any routing problem where the solver maintains a `@PlanningListVariable List<Visit> visits` on `Vehicle`. Shadow variables (auto-computed by Timefold whenever the route changes) keep running totals so the constraint body is a single `filter` or `penalize` call on `Vehicle` — no `join` or `groupBy` needed.

```java
// HARD — vehicle must not exceed its load capacity
Constraint vehicleCapacity(ConstraintFactory factory) {
    return factory.forEach(Vehicle.class)
            .filter(vehicle -> vehicle.getTotalDemand() > vehicle.getCapacity())
            .penalize(HardSoftScore.ONE_HARD,
                    v -> (int)(v.getTotalDemand() - v.getCapacity()))
            .asConstraint("Vehicle capacity");
}

// SOFT — minimize total driving time across all vehicles
Constraint minimizeTravelTime(ConstraintFactory factory) {
    return factory.forEach(Vehicle.class)
            .penalize(HardSoftScore.ONE_SOFT,
                    v -> (int)v.getTotalDrivingTimeSeconds())
            .asConstraint("Minimize travel time");
}
```

**Notes:**
- `getTotalDemand()` and `getTotalDrivingTimeSeconds()` are shadow variables annotated with `@ShadowVariable` (or computed via a `VariableListener`). Timefold keeps them updated automatically; the constraint just reads them.
- Penalizing the **excess** (`getTotalDemand() - getCapacity()`) rather than the total demand gives the solver a gradient: a vehicle overloaded by 10 units scores worse than one overloaded by 1 unit, guiding local search toward smaller violations.
- The same vehicle-centric pattern applies to: number of stops, total service time, overtime past depot closing, etc. If it can be aggregated as a shadow variable on `Vehicle`, the constraint is a one-liner `penalize` on `forEach(Vehicle.class)`.
- Do **not** try to replicate the aggregate with `groupBy(Visit::getVehicle, toSum(Visit::getDemand))` — it is slower and misses shadow-variable caching. Use the shadow variable approach whenever the aggregate is already computed there.

---

## 42. VRP — Time-Window Violation via Domain-Method Delegation

**Level:** HARD — each visit must complete service before its latest allowable end time.

**When to use:** VRP with time windows (VRPTW). The arrival time at a visit depends on the full route up to that point and is typically maintained as a shadow variable (`getArrivalTime()`). Delegate the violation check and magnitude to domain methods so the constraint body stays trivial.

```java
Constraint serviceFinishedAfterMaxEndTime(ConstraintFactory factory) {
    return factory.forEach(Visit.class)
            .filter(Visit::isServiceFinishedAfterMaxEndTime)
            .penalize(HardSoftScore.ONE_HARD,
                    v -> (int)v.getServiceFinishedDelayInMinutes())
            .asConstraint("Service finished after max end time");
}
```

Where the domain class encapsulates the arithmetic:

```java
// Inside Visit.java — computed from shadow variable arrivalTime
public boolean isServiceFinishedAfterMaxEndTime() {
    if (arrivalTime == null) return false;          // unassigned — no violation here
    return arrivalTime.plus(serviceDuration).isAfter(maxEndTime);
}

public long getServiceFinishedDelayInMinutes() {
    if (arrivalTime == null) return 0L;
    return ChronoUnit.MINUTES.between(maxEndTime, arrivalTime.plus(serviceDuration));
}
```

**Notes:**
- Delegation to domain methods (`isServiceFinishedAfterMaxEndTime`, `getServiceFinishedDelayInMinutes`) keeps the constraint clean and moves all `null`-guard and arithmetic into the domain object where it belongs.
- Always guard against `arrivalTime == null` in the domain method (unassigned visits have no arrival time). The `filter` will exclude them because the predicate returns `false`, but the penalty getter should also return `0L` defensively.
- The penalty is proportional to the delay in minutes (or seconds), giving the solver a gradient toward smaller violations rather than a flat penalty per visit.
- The exact same delegation pattern applies to: minimum start-time windows (`arrivalTime.isBefore(minStartTime)`), depot return deadlines (computed on `Vehicle`), and driver working-hour limits — any time-based constraint whose magnitude depends on route-order-sensitive shadow variables.

Pick the constraints you need and assemble them:

```java
public class EmployeeSchedulingConstraintProvider implements ConstraintProvider {

    }
```

## Tuning Constraint Weights

If you need different weights per constraint (not just ONE_HARD / ONE_SOFT), use multiplied scores:

```java
// Higher penalty for missing required skill vs other hard constraints
.penalize(HardSoftScore.ofHard(10))

// Weekend work is twice as undesirable as weekday work
.penalize(HardSoftScore.ofSoft(2))
```

For runtime-adjustable weights, see `@ConstraintConfiguration` and `penalizeConfigurable()` in the Timefold docs.

## 1. ConstraintProvider Interface

Every Timefold project needs exactly one class implementing `ConstraintProvider`:

```java
public class EmployeeSchedulingConstraintProvider implements ConstraintProvider {

    @Override
    public Constraint[] defineConstraints(ConstraintFactory factory) {
        return new Constraint[] {
            requiredSkill(factory),
            noOverlappingShifts(factory),
            unavailableEmployee(factory),
            balanceShifts(factory)
        };
    }

    // Each constraint is a separate method returning Constraint
    Constraint requiredSkill(ConstraintFactory factory) {
        return factory.forEach(Shift.class)
                .filter(shift -> !shift.getEmployee().getSkills()
                        .contains(shift.getRequiredSkill()))
                .penalize(HardSoftScore.ONE_HARD)
                .asConstraint("Required skill");
    }
    // ... more constraints
}
```

Rules:
- Constraint names must be unique across the entire `ConstraintProvider`.
- Each constraint method must accept `ConstraintFactory` as its only parameter (for testability with `ConstraintVerifier`).
- The method must return `Constraint` (the result of `.asConstraint("name")`).
- Quarkus auto-discovers the `ConstraintProvider` — no XML config needed.

## 2. The Constraint Pipeline

Every constraint stream follows this pipeline:

```
Source → [Filter] → [Join/IfExists] → [GroupBy] → [Map/Flatten] → Penalize/Reward → asConstraint
```

Minimum viable constraint:
```java
factory.forEach(Shift.class)
    .penalize(HardSoftScore.ONE_SOFT)
    .asConstraint("Penalize every shift");
```

Stream cardinalities:

| Cardinality | Prefix | Type |
|---|---|---|
| 1 | Uni | `UniConstraintStream<A>` |
| 2 | Bi | `BiConstraintStream<A, B>` |
| 3 | Tri | `TriConstraintStream<A, B, C>` |
| 4 | Quad | `QuadConstraintStream<A, B, C, D>` |

Max cardinality is 4. For higher, use `map()` to reduce to a tuple object first.

---

## 3. Stream Sources: forEach

| Method | Behavior |
|---|---|
| `forEach(Class)` | Selects all instances with non-null genuine planning variables. **Default choice.** |
| `forEachIncludingUnassigned(Class)` | Also includes entities whose planning variable is null (for `allowsUnassigned = true`). |
| `forEachUnfiltered(Class)` | Includes all instances regardless of variable state or consistency. |
| `forEachUniquePair(Class, Joiner...)` | Selects all unique pairs `(A, B)` where `A != B`, no duplicates. See §6. |

`forEach` works on both `@PlanningEntity` classes and problem fact classes registered via `@ProblemFactCollectionProperty`.

---

## 4. Filtering

```java
// Uni filter
factory.forEach(Shift.class)
    .filter(shift -> shift.getEmployee().getName().equals("Ann"))

// Bi filter (after join)
factory.forEach(Shift.class)
    .join(DayOff.class)
    .filter((shift, dayOff) -> shift.getDate().equals(dayOff.getDate()))
```

**Important:** Prefer Joiners over post-join filters for performance. Joiners use indexes; filters evaluate every combination.

---

## 5. Joining

`join()` creates a cartesian product between two streams (inner join). Always use Joiners to restrict matches:

```java
Constraint shiftOnDayOff(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .join(DayOff.class,
                Joiners.equal(Shift::getDate, DayOff::getDate),
                Joiners.equal(Shift::getEmployee, DayOff::getEmployee))
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("Shift on an off-day");
}
```

A join increases cardinality: Uni + join = Bi, Bi + join = Tri, Tri + join = Quad.

**Joiner evaluation caveat:** Multiple Joiners' mapping functions are evaluated independently — a later Joiner's lambda may run even when an earlier Joiner wouldn't match. Don't assume null-safety from earlier Joiners. Use `Joiners.filtering()` as a safe fallback if needed.

---

## 6. forEachUniquePair

Shorthand for joining a class with itself, producing only unique pairs (no `(A,A)`, no `(B,A)` if `(A,B)` exists):

```java
Constraint noOverlappingShifts(ConstraintFactory factory) {
    return factory.forEachUniquePair(Shift.class,
                Joiners.equal(Shift::getEmployee),
                Joiners.overlapping(Shift::getStart, Shift::getEnd))
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("No overlapping shifts");
}
```

This is **much better** than `forEach(Shift.class).join(Shift.class)` + filtering out duplicates manually. Always use `forEachUniquePair` when matching pairs of the same entity type.

---

## 7. Conditional Propagation: ifExists / ifNotExists

Use when you only need to check whether a matching object exists, without needing the matched object in the stream:

```java
// Penalize shifts where an unavailable employee is assigned
Constraint unavailableEmployee(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .ifExists(Availability.class,
                Joiners.equal(Shift::getEmployee, Availability::getEmployee),
                Joiners.equal(Shift::getDate, Availability::getDate),
                Joiners.filtering((shift, avail) ->
                    avail.getType() == AvailabilityType.UNAVAILABLE))
            .penalize(HardSoftScore.ONE_HARD)
            .asConstraint("Unavailable employee");
}
```

`ifExists` does NOT increase cardinality (unlike `join`). The stream stays Uni.
`ifNotExists` is the inverse — keeps elements where no matching object exists.

Both `ifExists` and `ifNotExists` work on **any** stream cardinality (Uni, Bi, Tri). When called on a `BiConstraintStream<A, B>`, the joiner lambdas for the "left side" receive both `A` and `B`:

```java
// On a BiConstraintStream<Employee, FlightAssignment>:
// "keep only the EARLIEST flight per employee"
.ifNotExists(FlightAssignment.class,
        equal((emp, fa) -> emp, FlightAssignment::getEmployee),
        greaterThan((emp, fa) -> fa.getDepartureUTCDateTime(),
                FlightAssignment::getDepartureUTCDateTime))
// If no OTHER assignment with an EARLIER departure exists → this IS the first
```

`ifExists` can also accept a problem-fact singleton (like a config object) to look up runtime settings:

```java
// Pair of talks with a mutual speaker
.forEachUniquePair(Talk.class,
        filtering((t1, t2) -> t2.hasMutualSpeaker(t1)))
// Check whether the pause between them satisfies the configured minimum
.ifExists(ConferenceConstraintProperties.class,
        filtering((t1, t2, config) ->
                !t1.getTimeslot().pauseExists(t2.getTimeslot(),
                        config.getMinimumConsecutiveTalksPauseInMinutes())))
.penalize(HardSoftScore.ofHard(1), Talk::combinedDurationInMinutes)
.asConstraint("Consecutive talks pause");
```

## 8. Grouping and Collectors

`groupBy()` groups stream elements by a key and applies collectors. It can increase or decrease cardinality.

```java
// Count shifts per employee
factory.forEach(Shift.class)
    .groupBy(Shift::getEmployee, ConstraintCollectors.count())
    // BiConstraintStream<Employee, Integer>
    .filter((employee, count) -> count > 5)
    .penalize(HardSoftScore.ONE_SOFT,
            (employee, count) -> count - 5)
    .asConstraint("Too many shifts");
```

groupBy supports 0-2 group keys and 0-4 collectors:

```java
// 0 keys + 1 collector → Uni result
.groupBy(count())

// 1 key + 0 collectors → Uni result (distinct keys)
.groupBy(Shift::getEmployee)

// 1 key + 1 collector → Bi result
.groupBy(Shift::getEmployee, count())

// 1 key + 2 collectors → Tri result
.groupBy(Shift::getEmployee, count(), sum(Shift::getHours))

// 2 keys + 1 collector → Tri result
.groupBy(Shift::getEmployee, Shift::getDate, count())
```

**Warning:** After `groupBy`, you lose access to the original objects. Only the keys and collector results are available.
Do NOT freestyle groupBys, follow the rules here strictly. Most groupBys are going to be 1 key + 1 collector (like: .groupBy(Shift::getEmployee, count())) or 2 keys + 1 collector (like: .groupBy(Shift::getEmployee, Shift::getDate, count())).
Getting creative with the .groupBys where you insert custom lambdas into the key fields and/or use more than 1 collector has been very error prone. Please stick to using the sugar syntax for the keys (like: Shift::getEmployee) and limit the number of keys to 1 or 2, and number of collectors to 1 - unless you have a very specific exception that needs more. In practice we mostly use 1 key + 1 collector, sometimes 2 keys + 1 collector. Having too many arguments in .groupBy has also been a problem, so try to stick to this.
Take this one very seriously as custom creative .groupBy have been one of your biggest problems when generating compileable and runnable constraint streams. It's fine to use a custom lambda with collectors like countDistinct(lambda), but inside key fields try to stick to simple sugar syntax, that's what we do in practice most of the time.
Also there always needs to be at least 1 key and 1 collector, do not create groupBys with just the collector for example.

**Exception — 0 keys + 1 collector (global aggregate):** The only valid case for a key-free `groupBy` is when you want a single global aggregate over ALL elements (e.g., the maximum end date across all jobs). This produces a `UniConstraintStream<T>` where `T` is the collector result:
```java
// Find the globally latest end date across all SINK allocations
factory.forEach(Allocation.class)
    .filter(a -> a.getJobType() == JobType.SINK && a.getEndDate() != null)
    .groupBy(ConstraintCollectors.max(Allocation::getEndDate))
    // UniConstraintStream<Integer> — single element: the max end date
    .penalize(HardSoftScore.ONE_SOFT, maxEndDate -> maxEndDate)
    .asConstraint("Total makespan");
```
This is a valid and useful pattern for global makespan or global minimum/maximum constraints.

**groupBy on Bi/Tri streams:** When `groupBy` is called on a `BiConstraintStream<A, B>`, the key/collector lambdas receive both `A` and `B`. Explicitly name them:
```java
// BiConstraintStream<Match, Team> — group by Team, use toConsecutiveSequences on matches
.groupBy((match, team) -> team,
         ConstraintCollectors.toConsecutiveSequences((match, team) -> match.getRound(), Round::getIndex))
```
Similarly, on a `TriConstraintStream<A, B, C>`, key lambdas have 3 parameters. Name them to keep the code readable.

## 9. Mapping, Flattening, Expanding, Complement

### map()
Transforms stream elements. Can decrease cardinality:

```java
// Bi → Uni (extract one field)
.join(Employee.class)
.groupBy((shift, employee) -> employee)  // equivalent to map

// Bi → Uni (create tuple)
factory.forEachUniquePair(Visit.class)
    .map((v1, v2) -> Pair.of(v1.getName(), v2.getName()))
```

### flattenLast()
Transforms a collection in the last position into individual stream elements:

```java
factory.forEach(Match.class)
    .groupBy(Match::getHomeTeam,
        ConstraintCollectors.toConsecutiveSequences(Match::getRoundId))
    .flattenLast(SequenceChain::getConsecutiveSequences)
    // Each consecutive sequence is now a separate tuple
```

`flattenLast` can also be applied directly after a `join` (not just after `groupBy`). It operates on the last tuple element, which must be a `Collection` or `Iterable`:

```java
// Explode a Set<LocalDate> carried on Employee into individual LocalDate elements
factory.forEach(Shift.class)
    .join(Employee.class, equal(Shift::getEmployee, Function.identity()))
    .flattenLast(Employee::getUnavailableDates)
    // Tri<Shift, Employee, LocalDate>
    .filter(Shift::isOverlappingWithDate)
    .penalize(...)
```

### expand()
Adds computed values to each tuple, increasing cardinality:

```java
factory.forEach(Shift.class)
    .expand(Shift::getDurationInHours)
    // Uni<Shift> → Bi<Shift, Integer>
```

`expand` is useful to cache an expensive or side-effect-prone method call — compute once, reuse in both `filter` and `penalize`:

```java
factory.forEach(Talk.class)
    .expand(Talk::missingSpeakerRequiredTimeslotTagCount)
    // Bi<Talk, Integer>
    .filter((talk, count) -> count > 0)
    .penalize(HardSoftScore.ofHard(1),
            (talk, count) -> count * talk.getDurationInMinutes())
    .asConstraint("Speaker required timeslot tags");
```

**Note:** `expand` increases cardinality: `Uni → Bi → Tri → Quad`. Maximum cardinality is 4, so you can call `expand` at most 3 times on a `UniConstraintStream`. After `expand`, you can also call `indictWith(...)` to control which objects are blamed for the violation.

### complement()
Adds missing problem facts to a grouped stream (critical for fairness/load balancing):

```java
factory.forEach(Shift.class)
    .groupBy(Shift::getEmployee, ConstraintCollectors.count())
    // BiStream<Employee, Integer> — only employees WITH shifts
    .complement(Employee.class, employee -> 0)
    // Now includes ALL employees; those without shifts get count = 0
```

---

## 10. Penalizing and Rewarding

Every constraint stream must end with a penalty or reward, then `.asConstraint("name")`:

```java
// Static weight — each match penalizes by exactly ONE_HARD
.penalize(HardSoftScore.ONE_HARD)
.asConstraint("Name");

// Dynamic weight — match weigher multiplies the base weight (int)
.penalize(HardSoftScore.ONE_SOFT, shift -> shift.getHours())
.asConstraint("Name");

// Reward (improves score)
.reward(HardSoftScore.ONE_SOFT)
.asConstraint("Name");

// Configurable weight (from ConstraintConfiguration)
.penalizeConfigurable()
.asConstraint("Name");
```

**Critical:** Every chain MUST end with `.asConstraint("unique name")`. Without it, the constraint silently doesn't exist.

**Optional post-scoring methods** (call before `.asConstraint`):
- `.justifyWith((a, score) -> new MyJustification(...))` — provides a human-readable score explanation object. The lambda arity matches the stream cardinality.
- `.indictWith((a, b) -> Collections.singleton(a))` — specifies which objects are "indicted" (blamed) for the violation. Useful when the penalized tuple contains computed intermediaries that are not meaningful to show to the user.

## 11. Joiners Reference

`import static ai.timefold.solver.core.api.score.stream.Joiners.*;`

| Joiner | Description | Example |
|---|---|---|
| `equal(Function)` | Same property on both sides | `equal(Shift::getEmployee)` |
| `equal(FunctionA, FunctionB)` | Different properties that must be equal | `equal(Shift::getDate, DayOff::getDate)` |
| `lessThan(FunctionA, FunctionB)` | A's value < B's value (Comparable) | `lessThan(Shift::getEnd, Shift::getStart)` |
| `lessThanOrEqual(...)` | A's value <= B's value | |
| `greaterThan(...)` | A's value > B's value | |
| `greaterThanOrEqual(...)` | A's value >= B's value | |
| `overlapping(startA, endA, startB, endB)` | Two intervals overlap | `overlapping(Shift::getStart, Shift::getEnd)` |
| `overlapping(startA, endA)` | Same-type shorthand (both sides use same getters) | Used with `forEachUniquePair` |
| `filtering(BiPredicate)` | Custom filter (slower — no indexing) | `filtering((a, b) -> a.overlaps(b))` |

**Never use `==` or `.equals()` in a post-join filter to match entities — always use `Joiners.equal()` for performance.**

**Joiners on higher-cardinality streams:** When calling `join()` or `ifExists()` on a `BiConstraintStream<A, B>` (introducing a third class `C`), the joiner lambda for the "left side" receives both `A` and `B`:
```java
// On a BiConstraintStream<Employee, FlightAssignment>, join with FlightAssignment:
.ifNotExists(FlightAssignment.class,
        equal((emp, fa) -> emp, FlightAssignment::getEmployee),
        greaterThan((emp, fa) -> fa.getDepartureUTCDateTime(),
                FlightAssignment::getDepartureUTCDateTime))
```
On a `TriConstraintStream<A, B, C>`, left-side lambdas are tri-functions. Always count arity to match cardinality.

**4-argument `overlapping` for cross-stream intervals:**
```java
overlapping(
    startExtractorForLeft,   // arity matches current stream cardinality
    endExtractorForLeft,
    startExtractorForRight,  // Function<RightClass, T>
    endExtractorForRight     // Function<RightClass, T>
)
```
Use when the two interval bounds come from different tuple elements (see §37 for a full example).

## 12. ConstraintCollectors Reference

`import static ai.timefold.solver.core.api.score.stream.ConstraintCollectors.*;`

| Collector | Return type | Description |
|---|---|---|
| `count()` | `int` | Count elements. Use `countBi()`, `countTri()`, `countQuad()` for higher cardinality. |
| `countLong()` | `long` | Long variant of count. |
| `countDistinct()` | `int` | Count unique elements. |
| `sum(ToIntFunction)` | `int` | Sum an int property. Variants: `sumLong()`, `sumBigDecimal()`, `sumDuration()`. |
| `average(ToIntFunction)` | `double` | Average of int property. Returns `null` for empty groups. |
| `min(Function)` | `T` | Minimum by Comparable property. |
| `max(Function)` | `T` | Maximum by Comparable property. |
| `toList()` | `List<T>` | Collect to list. **Disables incremental calculation — use sparingly.** |
| `toSet()` | `Set<T>` | Collect to set. Same performance caveat. |
| `toSortedSet()` | `SortedSet<T>` | Sorted set variant. |
| `toMap(keyFn, valueFn)` | `Map<K,V>` | Collect to map. |
| `loadBalance(Function)` | `LoadBalance` | Fairness metric. See §13. |
| `toConsecutiveSequences(Function)` | `SequenceChain` | Group into consecutive sequences. Use with `flattenLast()`. |
| `toConnectedTemporalRanges(startFn, endFn)` | `ConnectedRangeChain` | Group overlapping time ranges. |
| `toConnectedRanges(startFn, endFn, diffFn)` | `ConnectedRangeChain` | Non-temporal variant. |
| `conditionally(Predicate, collector)` | varies | Only applies collector when predicate is true. |
| `compose(collector1, collector2, mergerFn)` | varies | Combine 2-4 collectors into one. |
| `countBi()` | `int` | Count elements in a `BiConstraintStream`. Use after a join; `count()` only works on Uni streams. |
| `countTri()` | `int` | Count elements in a `TriConstraintStream`. |
| `countQuad()` | `int` | Count elements in a `QuadConstraintStream`. |
| `countDistinct(Function)` | `int` | Count distinct values of a function across the group. |
| `countDistinctLong(Function)` | `long` | Long variant of `countDistinct`. |
| `sumLong(ToLongFunction)` | `long` | Sum a long property. Use when values can exceed `Integer.MAX_VALUE`. |
| `sumBigDecimal(Function)` | `BigDecimal` | Sum a BigDecimal property. |
| `sumDuration(Function)` | `Duration` | Sum Duration values. |

**Arity rules for count variants:** Use `count()` on `UniConstraintStream`, `countBi()` on `BiConstraintStream`, `countTri()` on `TriConstraintStream`, `countQuad()` on `QuadConstraintStream`. Mismatching arity causes a compile error.

**min/max with mapping function (BiStream form):**
```java
// On a BiConstraintStream<Speaker, Talk>, find the Talk with the earliest start
min((Speaker speaker, Talk talk) -> talk,
     talk -> talk.getTimeslot().getStartDateTime())
// Returns: the Talk object with the minimum start time
```
The first lambda maps `(A, B) -> T` (selecting which object to return), the second extracts the `Comparable` key from `T`. Use this form when the collector is on a `BiConstraintStream`.

## 13. Load Balancing and Fairness

For fair distribution of work across employees, use the `loadBalance` collector:

```java
Constraint fairShiftDistribution(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .groupBy(ConstraintCollectors.loadBalance(Shift::getEmployee))
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Fair shift distribution");
}
```

To include employees with zero assignments (critical for fairness), use `complement()`:

```java
Constraint fairShiftDistribution(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .groupBy(Shift::getEmployee, ConstraintCollectors.count())
            .complement(Employee.class, employee -> 0)
            // Now all employees are in the stream, even those with 0 shifts
            .groupBy(ConstraintCollectors.loadBalance(
                    (employee, count) -> employee, (employee, count) -> count))
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Fair shift distribution");
}
```

**Note:** `unfairness()` returns a `BigDecimal`. Multiply by 1000 and cast to `int` for use with `HardSoftScore`.

**Shorthand form (1-arg) — no complement needed:**
If all load recipients always appear at least once in the stream (no zero-assignment case), use the single-argument shorthand:

```java
// All teams always have at least one assignment — no complement needed
Constraint fairAssignmentCount(ConstraintFactory factory) {
    return factory.forEach(TeamAssignment.class)
            .groupBy(ConstraintCollectors.loadBalance(TeamAssignment::getTeam))
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Fair assignment count per team");
}
```

**loadBalance on a BiConstraintStream — pair fairness:**
```java
// Balance how often each PAIR of teams confronts each other
Constraint evenlyConfrontationCount(ConstraintFactory factory) {
    return factory.forEach(TeamAssignment.class)
            .join(TeamAssignment.class,
                    equal(TeamAssignment::getDay),
                    lessThan(a -> a.getTeam().getId()))
            .groupBy(ConstraintCollectors.loadBalance(
                    (a, b) -> new Pair<>(a.getTeam(), b.getTeam())))
            .penalize(HardSoftScore.ONE_SOFT,
                    lb -> (int)(lb.unfairness().doubleValue() * 1000))
            .asConstraint("Evenly confrontation count");
}
public record Pair<A, B>(A key, B value) {}
```
The `loadBalance` `BiFunction` lambda receives both elements of the Bi stream and returns the "load recipient" key (the entity whose load we are balancing).

## 14. Score Types

`HardSoftScore` is the default. It has two levels: **hard** (must satisfy) and **soft** (optimize).

```java
@PlanningScore
private HardSoftScore score;
```

Use `HardMediumSoftScore` instead when the ProblemSpec ranks its objectives into two tiers above the tie-breakers — medium for the primary goal (coverage, selection, meeting targets), soft for quality preferences. `HardSoftScore` cannot express that ranking. See "Score Level Strategy" for the full guidance.

Whichever you pick, at least one constraint must sit at a non-hard level whenever `ProblemSpec.objectives` is non-empty — a provider of nothing but hard constraints has no objective function and cannot rank one feasible solution above another.

Common score constants:
```java
HardSoftScore.ZERO
HardSoftScore.ONE_HARD          // -1hard/0soft per match
HardSoftScore.ONE_SOFT          // 0hard/-1soft per match
HardSoftScore.of(0, -1)         // equivalent to ONE_SOFT
HardSoftScore.ofHard(2)         // -2hard penalty
HardSoftScore.ofSoft(3)         // -3soft penalty
```

**Never mix score types** within a single `ConstraintProvider`. All constraints must return scores of the same type.

## 16. Performance Tips

1. **Use Joiners, not post-join filters.** Joiners use hash indexes; filters evaluate every pair.

   ```java
   // BAD — creates full cartesian product, then filters
   factory.forEach(Shift.class)
       .join(DayOff.class)
       .filter((s, d) -> s.getEmployee().equals(d.getEmployee()))

   // GOOD — indexed join
   factory.forEach(Shift.class)
       .join(DayOff.class,
           Joiners.equal(Shift::getEmployee, DayOff::getEmployee))
   ```

2. **Use `ifExists`/`ifNotExists` instead of `join` when you don't need the joined object.** Join increases cardinality; ifExists does not.

3. **Use `forEachUniquePair` for same-entity pairs.** Never `forEach(X).join(X)` + manual dedup.

4. **Filter early.** Apply `filter()` as close to `forEach()` as possible to reduce downstream combinations.

5. **Avoid `toList()` and `toSet()` collectors when possible.** They disable incremental calculation for that group. Use `count()`, `sum()`, `min()`, `max()` instead.

6. **Don't use mutable objects as group keys.** Keys must have stable `hashCode()`. Planning entities are safe as keys only if their `hashCode` doesn't depend on planning variables.

7. **Precompute when possible.** If a calculation in `penalize(score, weigher)` doesn't depend on planning variables, compute it once in the domain model and cache it.

8. **Never chain two consecutive `.filter()` calls — always merge them into one.** Chaining `.filter()` immediately after another `.filter()` is redundant and unreadable. Always combine conditions with `&&`:
   ```java
   // WRONG — two filters in a row
   .filter(lesson -> lesson.getPreassignedRoom() != null)
   .filter(lesson -> !Objects.equals(lesson.getPreassignedRoom(), lesson.getRoom()))

   // CORRECT — one filter with both conditions
   .filter(lesson -> lesson.getPreassignedRoom() != null
           && !Objects.equals(lesson.getPreassignedRoom(), lesson.getRoom()))
   ```
   This applies regardless of how many conditions there are — combine all of them into a single `.filter(a && b && c)`. Never write `.filter(...).filter(...)`.

9. **Use `expand()` to avoid calling the same expensive method twice.** If a method is used in both `filter` and `penalize`, call `expand(Entity::expensiveMethod)` first to compute it once. The result is added to the tuple and reused.

10. **Use `flattenLast` instead of joining a collection class.** If an entity carries a `Set<X>` and you'd otherwise join against a separate collection of `X` objects, `flattenLast` on the entity's collection is cheaper than creating a separate stream.

11. **Avoid `filtering` joiner for indexed relationships.** `Joiners.filtering()` does a full cartesian scan with no indexing. Prefer `equal`, `lessThan`, `overlapping` wherever possible. Only use `filtering` for predicates that cannot be expressed with the other joiners (e.g., checking containment in a collection, or complex multi-field conditions).

## 17. Complete Employee Scheduling ConstraintProvider Example

```java
package com.example.scheduling.solver;

import ai.timefold.solver.core.api.score.buildin.hardsoft.HardSoftScore;
import ai.timefold.solver.core.api.score.stream.Constraint;
import ai.timefold.solver.core.api.score.stream.ConstraintFactory;
import ai.timefold.solver.core.api.score.stream.ConstraintProvider;
import ai.timefold.solver.core.api.score.stream.Joiners;

import com.example.scheduling.domain.Availability;
import com.example.scheduling.domain.AvailabilityType;
import com.example.scheduling.domain.Shift;

import java.time.Duration;

public class EmployeeSchedulingConstraintProvider implements ConstraintProvider {

    @Override
    public Constraint[] defineConstraints(ConstraintFactory factory) {
        return new Constraint[] {
            // Hard constraints
            requiredSkill(factory),
            noOverlappingShifts(factory),
            unavailableEmployee(factory),
            // Soft constraints
            preferredEmployee(factory),
            minimumRestBetweenShifts(factory)
        };
    }

    // --- HARD CONSTRAINTS ---

    Constraint requiredSkill(ConstraintFactory factory) {
        return factory.forEach(Shift.class)
                .filter(shift -> !shift.getEmployee().getSkills()
                        .contains(shift.getRequiredSkill()))
                .penalize(HardSoftScore.ONE_HARD)
                .asConstraint("Required skill");
    }

    Constraint noOverlappingShifts(ConstraintFactory factory) {
        return factory.forEachUniquePair(Shift.class,
                    Joiners.equal(Shift::getEmployee),
                    Joiners.overlapping(Shift::getStart, Shift::getEnd))
                .penalize(HardSoftScore.ONE_HARD)
                .asConstraint("No overlapping shifts");
    }

    Constraint unavailableEmployee(ConstraintFactory factory) {
        return factory.forEach(Shift.class)
                .join(Availability.class,
                    Joiners.equal(Shift::getEmployee, Availability::getEmployee),
                    Joiners.equal(Shift::getDate, Availability::getDate))
                .filter((shift, avail) ->
                        avail.getType() == AvailabilityType.UNAVAILABLE)
                .penalize(HardSoftScore.ONE_HARD)
                .asConstraint("Unavailable employee");
    }

    // --- SOFT CONSTRAINTS ---

    Constraint preferredEmployee(ConstraintFactory factory) {
        return factory.forEach(Shift.class)
                .join(Availability.class,
                    Joiners.equal(Shift::getEmployee, Availability::getEmployee),
                    Joiners.equal(Shift::getDate, Availability::getDate))
                .filter((shift, avail) ->
                        avail.getType() == AvailabilityType.PREFERRED)
                .reward(HardSoftScore.ONE_SOFT)
                .asConstraint("Preferred employee");
    }

    Constraint minimumRestBetweenShifts(ConstraintFactory factory) {
        return factory.forEachUniquePair(Shift.class,
                    Joiners.equal(Shift::getEmployee))
                .filter((s1, s2) -> {
                    Duration gap = Duration.between(s1.getEnd(), s2.getStart());
                    if (gap.isNegative()) {
                        gap = Duration.between(s2.getEnd(), s1.getStart());
                    }
                    return !gap.isNegative() && gap.toHours() < 12;
                })
                .penalize(HardSoftScore.ONE_SOFT,
                        (s1, s2) -> {
                            Duration gap = Duration.between(s1.getEnd(), s2.getStart());
                            if (gap.isNegative()) {
                                gap = Duration.between(s2.getEnd(), s1.getStart());
                            }
                            return (int) (12 - gap.toHours());
                        })
                .asConstraint("Minimum 12h rest between shifts");
    }
}
```

## 1. Domain Model Design Checklist

Follow this process when designing your domain model:

1. **Draw a class diagram.** Identify all classes and their relationships.
2. **Create sample instances.** E.g., Employee: Ann, Beth, Carl. Shift: Monday-Morning, Monday-Evening.
3. **Color the relationships that change during planning orange.** These become planning variables.
4. **Color relationships derived from planning variables purple.** These become shadow variables.
5. **Ensure every planning entity has at least one problem property** (a field that is NOT a planning variable). A planning entity cannot consist solely of planning variables + ID.
6. **Minimize planning variables.** Every additional planning variable exponentially increases the search space. If one variable can be derived from another, make it a shadow variable.
7. **Verify:** when all planning variables are null, is the entity still describable? E.g., "the Monday 6AM-2PM Cook shift" makes sense even before an employee is assigned.

---

## 2. Choosing the Planning Entity

**The class that changes during planning is the planning entity.** The field that the solver fills in is the planning variable.

For employee scheduling:

| Pattern | Planning Entity | Planning Variable | When to use |
|---|---|---|---|
| **Shift → Employee** | Shift | `employee` | Most common. "Assign an employee to each shift." |
| **ShiftAssignment** | ShiftAssignment | `employee` (and/or `shift`) | When many-to-many (see §5) |
| **Employee → List<Shift>** | Employee | `@PlanningListVariable shifts` | When ordering matters (routing-style) |

**Recommended for employee scheduling:** Shift as planning entity, Employee as planning variable value. This is the pattern used in the official quickstarts.

```java
@PlanningEntity
public class Shift {
    @PlanningVariable   // Solver assigns this
    private Employee employee;

    // Problem properties (fixed during solving)
    private LocalDateTime start;
    private LocalDateTime end;
    private String requiredSkill;
}
```

## 3. Overconstrained Planning

When there aren't enough employees to fill all shifts (more shifts than available employee-hours), the solver will break hard constraints trying to assign everyone. Instead, allow some shifts to be unassigned.

### Step 1: Allow unassigned

```java
@PlanningVariable(allowsUnassigned = true)
private Employee employee;
```

### Step 2: Pick the score type

Two tiers (`HardSoftScore`) is enough when "assign as much as possible" is the only goal above the tie-breakers. Use `HardMediumSoftScore` when the spec also ranks its remaining goals — coverage at medium, preferences at soft. See "Score Level Strategy" below.

```java
@PlanningScore
private HardMediumSoftScore score;
```

### Step 3: Make assignment worth something

This constraint is not optional. Without it the solver has no reason to assign anything, and every other constraint on the entity goes dead (Step 4).

```java
Constraint assignEveryShift(ConstraintFactory factory) {
    return factory.forEachIncludingUnassigned(Shift.class)
            .filter(shift -> shift.getEmployee() == null)
            .penalize(HardMediumSoftScore.ONE_MEDIUM, Shift::getPriorityWeight)
            .asConstraint("Assign every shift");
}
```

Weight it by whatever the ProblemSpec says makes one entity more worth assigning than another (priority, value, urgency, lateness). A flat weight tells the solver every entity is equally worth having, which is almost never what the spec says.

### Step 4: Switch every constraint on that entity to forEachIncludingUnassigned

**`forEach()` emits an entity only when ALL of its genuine planning variables are assigned.** Once a variable is `allowsUnassigned = true`, any entity where it is null vanishes from `forEach()` — silently, from every constraint rooted in that entity, not just the ones about that variable. Leaving `forEach()` in place here is the most common way to ship a solver that scores `0hard/0soft` on every input.

```java
// WRONG once Shift.employee is allowsUnassigned — unassigned shifts are
// invisible here, so this constraint cannot see the very shifts it should judge
factory.forEach(Shift.class)
    .filter(shift -> !shift.getEmployee().getSkills()...)

// CORRECT — see every shift, guard the null explicitly
factory.forEachIncludingUnassigned(Shift.class)
    .filter(shift -> shift.getEmployee() != null && !shift.getEmployee().getSkills()...)
```

Apply this to `forEachUniquePair(Shift.class, ...)` too — it is built on `forEach()` and inherits the same filter.

**Score level guidance:**
- **Hard:** Must not be violated (physical impossibilities, legal requirements)
- **Medium:** "Assign as much as possible" — penalize unassigned entities here
- **Soft:** Optimization preferences (fairness, employee preferences)

## 4. Pinning (Immovable Entities)

Pinned entities are locked to their current values. The solver cannot change them.

### Use cases
- Past shifts that are already worked
- Manually assigned shifts that a manager locked in
- Shifts in a continuous planning window that have passed the "freeze" point

### Implementation

```java
@PlanningEntity
public class Shift {

    @PlanningPin
    private boolean pinned;

    @PlanningVariable
    private Employee employee;

    // ...
}
```

If `pinned == true`, the solver will not change the employee assignment for this shift, even if the current value is suboptimal. The solver plans around pinned entities.

**Important:** A pinned entity with a null planning variable and `allowsUnassigned = false` will throw an exception in Timefold 1.10+. If a shift is pinned, it must already have a valid assignment (or use `allowsUnassigned = true`).

## 5. Many-to-Many Relationships

If your problem has a many-to-many relationship (e.g., multiple employees can be assigned to the same shift, and each employee works multiple shifts), introduce an intermediate assignment class.

### Before (broken)
```
Shift ←→ Employee  (many-to-many)
```

### After (correct)
```
Shift ←one-to-many→ ShiftAssignment ←many-to-one→ Employee
              (problem fact)     (planning entity)    (planning variable)
```

```java
@PlanningEntity
public class ShiftAssignment {
    @PlanningId
    private String id;

    // Problem property (fixed)
    private Shift shift;

    // Planning variable (solver assigns this)
    @PlanningVariable
    private Employee employee;
}
```

The `@PlanningSolution` then has:
```java
@PlanningEntityCollectionProperty
private List<ShiftAssignment> assignments;

@ProblemFactCollectionProperty
@ValueRangeProvider
private List<Employee> employees;

@ProblemFactCollectionProperty
private List<Shift> shifts;
```

**When to use:** Only when you need multiple employees per shift slot. If each shift needs exactly one employee, use the simpler Shift-as-entity pattern from §2.

## 6. Multiple Planning Variables

A planning entity can have multiple planning variables. For school timetabling, a Lesson has both `timeslot` and `room`:

```java
@PlanningEntity
public class Lesson {
    @PlanningVariable
    private Timeslot timeslot;

    @PlanningVariable
    private Room room;
}
```

**Caution:** Each additional planning variable multiplies the search space. With N entities, V1 values for variable 1, and V2 values for variable 2, the search space is `(V1 × V2)^N`. Only add a second planning variable if the solver genuinely needs to choose both independently.

For employee scheduling, typically only `employee` is a planning variable. The shift's time and role are fixed inputs.

## 7. Score Level Strategy

Pick the score type from the number of priority tiers the ProblemSpec actually uses, then apply it consistently across the `@PlanningScore` field, every `.penalize(...)`/`.reward(...)` call and the `SolutionManager` generic parameter.

**`HardSoftScore` — the default, for two tiers:**
- **Hard:** physical/legal impossibilities that must never be violated.
- **Soft:** preferences and quality objectives to optimize.

**`HardMediumSoftScore` — when the spec ranks its goals into two levels above the tie-breakers.** Use it whenever the ProblemSpec distinguishes objectives that matter more from objectives that matter less — wording like "primary/secondary", "more important than", "medium-priority", or an objectives list that is explicitly ordered by priority. `HardSoftScore` cannot express that ranking, and squashing both tiers into `soft` lets a handful of small preferences outvote the thing the user actually cares about.

```java
import ai.timefold.solver.core.api.score.buildin.hardmediumsoft.HardMediumSoftScore;

@PlanningScore
private HardMediumSoftScore score;

// ... HardMediumSoftScore.ONE_HARD / .ONE_MEDIUM / .ONE_SOFT,
//     HardMediumSoftScore.ofMedium(n) / .ofSoft(n)
```

- **Hard:** must never be violated.
- **Medium:** the primary goal — "schedule as many as possible", "assign every entity", "meet the targets". Selection and coverage live here.
- **Soft:** tie-breakers and quality preferences — fairness, balance, utilization, idle gaps.

**Whichever you choose, there must be constraints at the non-hard levels.** A provider whose constraints are all hard has no objective function: every feasible solution scores identically and the solver returns an arbitrary one.

For overconstrained problems (not all entities can be assigned), use `allowsUnassigned = true` and reward assigned entities — or penalize unassigned ones — at the medium level with a weight that reflects their importance.

**Never use float/double in scores.** They cause score corruption due to floating-point arithmetic. Use scaled `int` instead (e.g., multiply by 1000 and cast to int).

## 8. Backup Planning

For resilience against unexpected changes (employee calls in sick), build buffer into the plan:

```java
// Soft constraint: Keep one "spare" employee per time period
Constraint spareEmployee(ConstraintFactory factory) {
    return factory.forEach(Shift.class)
            .groupBy(Shift::getTimePeriod, countDistinct(Shift::getEmployee))
            .filter((period, employeeCount) ->
                    employeeCount >= period.getRequiredEmployees())
            // No spare if all slots are filled by unique employees
            // Reward having MORE employees than required
            .reward(HardSoftScore.ONE_SOFT)
            .asConstraint("Spare employee capacity");
}
```

This creates slack in the schedule so that when an employee calls in sick, another can cover without replanning.

## 9. Constraint Weight Strategy

**Don't overthink weights at the start.** Begin with `ONE_HARD` / `ONE_SOFT` for everything. Iterate with stakeholders later.

Guidance:

| Approach | Code | When |
|---|---|---|
| **Fixed weights** | `penalize(HardSoftScore.ONE_HARD)` | Prototype, simple problems |
| **Scaled fixed weights** | `penalize(HardSoftScore.ofSoft(10))` | When some soft constraints are more important |
| **Configurable weights** | `penalizeConfigurable()` + `@ConstraintConfiguration` | When business users need to tune weights via UI |

For configurable weights, see `@ConstraintConfiguration` and `@ConstraintWeight` in the Timefold docs. This enables runtime tuning without code changes.

## 10. Time Grain Pattern vs Direct Assignment

Two common ways to model time in scheduling:

### Direct Assignment (recommended for employee scheduling)
Shifts have fixed start/end times. The solver assigns employees to shifts.

```java
class Shift {  // fixed time, variable employee
    LocalDateTime start;
    LocalDateTime end;
    @PlanningVariable Employee employee;
}
```

### Time Grain Pattern (for timetabling/meeting scheduling)
Time is divided into discrete grains. The solver assigns entities to grains.

```java
class Lesson {  // variable time slot and room
    @PlanningVariable Timeslot timeslot;
    @PlanningVariable Room room;
}
```

**For employee scheduling, use Direct Assignment.** The shifts are pre-defined with fixed times; only the employee assignment changes. Time Grain is for problems where the solver also chooses *when* things happen.
