## Review in priority order

1. Requirement coverage
   Cross-check constraints AND objectives, OriginalRequest and UserClarifications
   against the implementation. Preserve explicit removals, units, boundaries,
   weights and priorities. domainContext is terminology, not additional rules.
   Ensure every real constraint is registered in defineConstraints(); no stubs,
   dummy constant penalties, omitted objectives or convenient proxy objectives.
   At most N permits N; ordered need not be consecutive. Do not weaken a rule
   to make generated examples feasible.

2. Domain and identity
   Per-solution facts and derived context must not use mutable static fields:
   initializing or solving one problem must not affect another. Keep that
   context on each solution or its entities; immutable constants and stateless
   shared helpers are fine.
   Exactly one @PlanningSolution, HardSoftScore and a visible top-level
   SolverStatus field. Register every genuine AND shadow @PlanningEntity.
   A valid entity may have basic variables, list variables, OR only shadows;
   do not invent a basic @PlanningVariable on a shadow-only/list entity.
   Match variable types and explicit valueRangeProviderRefs to range IDs.
   Named entity-local providers require matching refs just like solution-level
   providers. Preserve immutable per-entity eligibility; never expand a range.
   Initialize collections/singletons and planning lists, use stable @PlanningId
   values, no double registration as both entity and problem fact.
   Check @ShadowVariable supplierName matches a method with @ShadowSources and
   complete mutable dependencies. Listener-based shadows use variableListenerClass.
   Keep public no-arg constructors and valid accessors; preserve working explicit
   methods, Lombok, computed getters and partial constructors. No style rewrites.
   Fixed relationship facts referencing planning entities need @DeepPlanningClone
   (ai.timefold.solver.core.api.domain.solution.cloner) on their declared class;
   the collection must use that class as its element type. Ordinary facts with
   only immutable references do not need deep cloning. JSON identity is separate.

3. Constraint Streams
   ConstraintProvider is an interface, not an annotation. Validate current tuple
   arity after each operation. count() returns Integer, countLong() returns Long;
   collectors take all current tuple elements. groupBy produces keys + collector
   results, up to four elements; one collector alone produces Uni.
   join's right operand is a Class or Uni stream, not a grouped Bi stream.
   flattenLast replaces the last element; expand adds one.
   complement exists: minimum-coverage/fairness aggregation must include resources
   with zero assignments, including after inner joins. Upper-bound-only rules do
   not need artificial minimum penalties. Use real global max for makespan.
   Positive HardSoftScore weights; penalize subtracts, reward adds. Nonnegative
   match weights, safe integer scaling/overflow, no '/' in constraint names.
   Check waiting plus service before finish-by windows and both depot route legs.
   Join referenced planning entities into relationship-fact streams: reading
   their variables only through a shared fact hides incremental dependencies.

4. JSON import/export
   Shared assignments must reference canonical value-range instances after JSON
   loading. Check scoped @JsonIdentityInfo IDs and full canonical collections;
   do not emit only IDs without definitions. Do not silently append forbidden
   values. Ignore entity-reference shadows to avoid cycles, not useful scalar
   shadows merely because they are derived. Keep solverStatus serialized.
   Both standalone IO and REST must support native generated JSON round trips.
