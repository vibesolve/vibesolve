## Modeling decisions

- Fixed data is a problem fact. A class with a solver-assigned field is a genuine
  planning entity. A class with only derived shadow variables is a shadow entity:
  it also needs @PlanningEntity, but NOT an invented genuine planning variable.
- Use basic @PlanningVariable fields for independent assignments; use
  @PlanningListVariable for ordered membership, e.g. Vehicle.visits.
  Do not introduce time-slot decisions if times are fixed input.
- Ordered need not mean consecutive; at most N is not exactly N; preferences
  are not hard restrictions. Include the data and finite input bounds needed
  for explicitly prioritized objectives.
- Domain helpers may compute derived values but must be pure. Never change a
  planning variable while computing a getter/hash/score. Constraints come later.

## Identity, construction and JSON

- Every entity and shared fact has a non-null @PlanningId unique within its
  class. IDs stay fixed during solving. Do not reuse one ID for distinct objects.
  Hash/equality must not include mutable planning variables; prefer object
  identity or stable IDs. Avoid Lombok @Data equality over assignments/cycles.
- Give JSON domain classes and the solution public no-arg constructors and
  appropriate getters/setters, using Lombok or explicit methods consistently.
  Computed accessors and partial constructors are fine.
  Avoid @AllArgsConstructor on classes with shadows: callers must not initialize
  solver-managed shadow fields. No duplicate generated/manual methods.
- JSON must preserve shared identity: assignments deserialize to the SAME
  instances as their value-range entries. For referenced entities/facts use
  @JsonIdentityInfo(generator = ObjectIdGenerators.PropertyGenerator.class,
  property = "id", scope = ActualDomainClass.class), adapting the ID property.
  Scope each ID namespace so Room("1") and Exam("1") do not collide.
- Expose full canonical fact/entity collections on the solution, not only IDs.
  Serialize value collections before their referencing collections using
  @JsonPropertyOrder when needed. Field-level @JsonIdentityReference(alwaysAsId
  = true) can encode references when full definitions exist in the same document.
  Do not make an entire canonical collection emit only IDs.
- @JsonIgnore entity-reference shadows (inverse owner, previous/next element,
  inverse collections) to prevent cycles. Scalar shadows (int, String,
  LocalDateTime) do not create cycles: keep useful values visible. Timefold
  recomputes shadows; do not trust client-supplied values as authoritative.
- Keep solverStatus visible on the solution. Use the top-level
  ai.timefold.solver.core.api.solver.SolverStatus, not SolverManager.SolverStatus.

## Planning clones are not JSON round trips

Timefold clones planning entities but normally shares problem facts. A fixed
relationship fact holding entity references (e.g. a conflict pair) must follow
those entities into each solution clone. Annotate that fact's declared class
with @DeepPlanningClone from ai.timefold.solver.core.api.domain.solution.cloner;
use that actual class as the solution collection's element type. Annotating only
a runtime subtype behind a different declared type is insufficient. Do not
deep-clone ordinary facts that only reference immutable facts. Existing ID-based
relationships need no entity-reference cloning; preserve a correct design.
@JsonIdentityInfo, matching IDs and REST-only reference normalization do NOT fix
stale entity references inside a planning clone. Do not invent genuine planning
variables on fixed relationship facts to make cloning happen.

## Solution and value ranges

- Exactly one @PlanningSolution has @PlanningScore HardSoftScore score,
  solverStatus, @PlanningEntityCollectionProperty for each entity class, and
  @ProblemFactCollectionProperty / @ProblemFactProperty for fixed facts.
- Initialize every annotated collection to a mutable empty/populated list,
  never null. Initialize required singleton facts (calendar/config/matrix).
- Register each object once: an entity collection is not also a fact collection.
  A fact collection may also have @ValueRangeProvider; a collection of shadow
  entities may have entity-collection plus value-range annotations.
- Use explicit named ranges and matching valueRangeProviderRefs. A basic
  variable's range can be on the solution OR entity. A named entity-local range
  is referenced exactly like a named solution range. Unnamed ranges can auto-match
  by type, but do not mix that approach with named references.
- Entity-local ranges are immutable per-entity eligibility. Never add values
  to legalize an out-of-range assignment or derive a range from mutable planning
  variables. Multiple same-typed variables need the correct explicit range IDs.
  Return stable collections with no null/duplicate instances; nonempty whenever
  required assignment needs a value.
- Basic planning variables use boxed/object types, not primitive int/long.
  Use allowsUnassigned = true only if the domain permits it; any requested
  unassignment penalty belongs in constraints later.
- List value ranges belong on the solution. Initialize each planning list to
  new ArrayList<>(); an element must not appear in two planning lists.

## List planning and shadows

Vehicle owns @PlanningListVariable(valueRangeProviderRefs = "visitRange")
List<Visit> visits; Visit is a shadow @PlanningEntity. The solution registers
vehicles and visits separately as entity collections, and supplies
@ValueRangeProvider(id = "visitRange") on the canonical visits collection.
On Visit, sourceVariableName must exactly match Vehicle.visits:

~~~java
@InverseRelationShadowVariable(sourceVariableName = "visits")
@JsonIgnore
private Vehicle vehicle;

@PreviousElementShadowVariable(sourceVariableName = "visits")
@JsonIgnore
private Visit previousVisit;

@ShadowVariable(supplierName = "arrivalTimeSupplier")
private LocalDateTime arrivalTime;

@ShadowSources({"vehicle", "previousVisit", "previousVisit.arrivalTime"})
public LocalDateTime arrivalTimeSupplier() {
    if (vehicle == null) return null;
    if (previousVisit == null) {
        return vehicle.getDepartureTime().plusMinutes(
                vehicle.getDepot().travelMinutesTo(location));
    }
    LocalDateTime departure = previousVisit.getDepartureTime();
    return departure == null ? null : departure.plusMinutes(
            previousVisit.getLocation().travelMinutesTo(location));
}

public LocalDateTime getDepartureTime() {
    if (arrivalTime == null) return null;
    LocalDateTime serviceStart = arrivalTime.isBefore(earliestStart)
            ? earliestStart : arrivalTime;
    return serviceStart.plusMinutes(serviceMinutes);
}
~~~

Adapt time types, names and travel lookup to actual input. Implement every
referenced helper. BOTH @ShadowVariable(supplierName = "...") and the supplier's
@ShadowSources are required. Track ALL mutable dependencies; for collections use
paths such as predecessorAllocations[].endDate. Suppliers return values without
mutating other entities; unassigned dependencies can be null during initialization.
Immutable facts do not need change tracking. Do not use recursive getters to
work around cyclic dependencies.

Prefer declarative suppliers for new derived shadows where appropriate.
Listener-based shadows use @ShadowVariable(variableListenerClass = ...,
sourceVariableName = "..."). Use VariableListener for basic-variable sources
and ListVariableListener for list-variable sources, with their corresponding
before/after callbacks and ScoreDirector notifications.
Do not invent annotation attributes or mix listener and supplier forms.

## DataGenerator

- Provide public generate() for a small realistic unsolved sample and
  generate(long seed) for reproducible tests. Use Random(seed), no wall clock
  or UUID randomness in the seeded overload. Return fresh object graphs.
- Generate diverse but feasible facts: enough capacity, compatible skills,
  nonempty eligible ranges and achievable windows. Construct a feasible witness
  internally if useful, then clear assignments before returning. Do not weaken
  rules to make random samples feasible.
- Exercise multi-valued requirements with a sample needing two values together
  when the domain supports them. Preserve an explicitly supplied sample exactly;
  seeded generation does not authorize changing the user's fixed input facts.
- Leave basic @PlanningVariable fields null and @PlanningListVariable lists
  empty: the solver does the assigning. Leave shadows at defaults; initialize
  inverse shadow collections to mutable lists.
- Use canonical instances in fixed relationships, including eligibility lists.
  Initialize all matrices, singletons and collections. Use actual constructors
  and getters; lambda-captured loop indices must be final/effectively final.
- Keep samples small enough for five 15-second FULL_ASSERT solves plus REST
  testing within the suite's bounded runtime.
